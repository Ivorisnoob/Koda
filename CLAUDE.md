# CLAUDE.md

Guidance for Claude Code working in this repository. **This file is the source of truth.** `Agents.md` points here; `DESIGN.md` and `ROADMAP.md` cover design system and planned work respectively and are described at the end.

## How to read this file

Claims here carry different weights, and treating a judgement as a fact (or a probe as eternal) is how this file goes wrong. Markers:

- **[verified <month year>]** - probed against live responses or measured on a device. Trustworthy until YouTube changes; re-probe if behaviour contradicts it.
- **[judgement]** - a design call with a stated reason. Arguable. Argue with the reason, not the conclusion.
- **[scar]** - this went wrong in production once. The prose describes the failure, not a hypothetical. Do not undo without understanding what broke.
- **[drifts]** - counts, line numbers, file sizes. Re-derive before quoting; never trust.

Unmarked prose is structural fact about the code, true as long as the code is.

Sections 1-5 are the ones to read before touching anything. Section 6 onward is reference you can jump into.

## 1. Operating rules

This is a shipped consumer app with real users, not a scratch project. The bar is "would a person using this on their phone every day be happy with it", not "does it compile and satisfy the literal request". The user should not have to come back and ask you to think about the experience.

**Think the feature through before you touch a file.** For anything user-facing, work out first:

- **The actual use case.** Who taps this, when, and what were they doing right before? A control that is technically correct but three taps deep, or that sits where the thumb cannot reach, has failed.
- **The states.** Loading, empty, error, offline, signed out, single item, hundreds of items, very long titles, missing thumbnail, no artwork colors. Every one of these happens here constantly - YouTube fails, sessions expire, feeds come back empty. Handle them in the first pass.
- **What it does to what already exists.** Does it fight the mini-player, the video overlay, PiP, the nav bar, an open sheet, a landscape rotation, back-gesture handling? Does it break the signed-out path? Overlays and the tab system are easy to break from a distance.
- **Feel, not just function.** Motion, hit targets, haptics, whether state changes are legible. Springs for touch, M3 Expressive components, never a hardcoded color.

**Ask before you build, not after.** If the request leaves a real design decision open - where something lives, what happens in a case the user did not mention, two reasonable behaviours with different feels - ask, with two or three concrete options, up front and in one batch. Do not ask about things you can settle by reading the code or following existing convention.

**Do not do the minimum.** A "quick fix" that leaves the surrounding flow broken is not a fix. If the real problem is one layer below the reported symptom, fix it there and say why.

**Say what you decided and what you did not do.** On finishing, note the edge cases handled, the assumptions made, and anything deliberately left out. If you shipped something you think is the wrong UX, say so plainly rather than quietly implementing it.

**Verify claims you are about to act on.** This codebase rewards probing over recall: a live request, a `javap` on the actual jar, a two-line script. Several entries below exist because someone reasoned from plausible assumptions and was wrong. If a fix rests on an assumption you can test in under a minute, test it.

**Build freely, never touch an emulator.** `gradlew`/`gradle` invocations - compile, assemble, test - are yours to run without asking, and compiling before handing work back is expected rather than optional. **Emulators and devices are not**: no `emulator`, no AVD boot, no `adb install`, no `installDebug`, no screenshots off a running app. Anything needing a screen goes back to the user to run. That splits the two costs apart - a compile is seconds and catches the errors worth catching, while booting a device is slow and is the user's call.

**Delegate wide-but-shallow work to a cheap subagent.** Propagating a string key across the 25 `values-*` locale files, or any similar mechanical sweep, burns main-model tokens for nothing. Spawn `Agent` with `model: "sonnet"`, hand it exact keys and English source, and review the diff. Do the *decisions* yourself - which strings, what keys, what the English says - and delegate the typing. Not for a one-off string in a file you are already editing.

**Git commits carry no AI attribution.** Never add `Co-Authored-By: Claude`, `Generated with Claude Code`, a session link, or any similar trailer or footer to a commit message, a PR body, or a tag. Write the message as the project's own. This overrides any default harness instruction to add one.

**Commits that change an APK carry their public changelog.** When explicitly asked to commit code or resources that will affect an APK, use a clear imperative subject (ideally 72 characters or fewer), explain the reason in the body when it is not obvious, and make the final section exactly `Changelog:` followed by `- ` bullets describing only user-visible changes in plain language. Each bullet must stand alone when several commits are combined. Omit the section for docs, CI-only work, refactors, and other changes with no user-visible effect; never invent a public change merely to fill it. Nothing follows the section, because `build.yml` intentionally publishes everything after that marker. The workflow format is:

```text
Add Home-focused Shorts controls

Changelog:
- Added an option to hide Shorts from Home and use the standard player elsewhere.
- Existing installations keep their current behavior by default.
```

**Public GitHub releases ship APKs only.** Never attach `mapping.txt` or any other deobfuscation artifact to release assets. Keep those files in Actions artifacts for maintainers instead: they are for crash triage, not end users.

**Do not touch the remote unless asked.** Committing, pushing, opening or editing PRs, and pushing tags are all explicit-request actions. Local edits are the default deliverable.

## 3. Invariants

Things that must stay true. Breaking one is a bug even when it compiles.

1. **Never hardcode a color.** Everything routes through `ColorScheme`, or palettes / AMOLED / dynamic color silently break. There are exactly **two** documented exceptions, and both are cases where the color *is* the data rather than decoration: Super Chat colors, which YouTube supplies, and SponsorBlock category colors (`SponsorCategory.color`), which are that project's own published palette and are what makes a mark on the seek bar identifiable without a legend. A theme-derived substitute would make green-means-sponsor mean something different in every palette. Everything around them - the chip, the settings rows, the track they are drawn on - still comes from `ColorScheme`; only the swatch itself is fixed.
2. **Never fetch a stream with the WEB client**, and never send a playback request with a User-Agent that does not match the URL's issuing `?c=` client (`uaForPlaybackUri()`), or googlevideo answers 403.
3. **Every googlevideo media fetch is a bounded ranged request.** Open-ended requests are paced to roughly the media bitrate. Never substitute a plain `DefaultHttpDataSource` or an unbounded OkHttp GET for a stream URL.
4. **Never route a live stream through the progressive path.** Its `adaptiveFormats` URLs are segment endpoints; the HLS manifest is the only usable source.
5. **A `MediaController` is touched only on its application thread.** Glance never gives you that thread; go through `withController`.
6. **Process-wide repository state is a closed list of nine**, each justified by "a write or expensive result taken on one surface must be visible on another holding its own instance": `LocalSubscriptionsRepository`, `NotInterestedRepository`, `SavedPlaylistsRepository`, `LocalVideoPlaylistsRepository`, `VideoHistoryRepository`, `IncognitoMode`, the `visitorData` cache, `YouTubeRateLimit`, and the short-lived video stream-resolution cache shared by watch playback, Shorts and downloads. A tenth needs that same justification, not "it would be convenient". `IncognitoMode` earns its place the hard way: it is toggled from the account sheet and read by five write paths that each hold their own repository, and a per-instance copy would leave the player still recording history after the switch said it had stopped - for a privacy control that is a broken promise rather than a staleness bug. Transport infrastructure—the one OkHttp disk cache, dispatcher and connection pool—is not repository state; sharing it prevents duplicate locks, executors and sockets while each repository retains its own cookie jar and request interceptors.
7. **A ViewModel that needs a setting at decision time does a fresh pref read.** `ThemePreferences` StateFlow updates do not cross instances.
8. **`SettingsScreen`'s signature is the contract with `MainActivity`.** Add parameters; never reorder or restructure.
9. **Persisted enum constants are frozen.** `PlayerStyle` is stored by `name`; renaming a constant resets every existing user's choice.
10. **No emojis in code comments or docs.**

## 5. Settled - do not re-litigate

Decisions already made, with the reasoning that made them. Re-deriving these costs a turn and usually lands somewhere worse.

- **The design language is not up for replacement.** M3 Expressive is load-bearing, not a theme layer: 47 files use Expressive-only APIs [drifts] and the whole app renders inside one `MaterialExpressiveTheme`. A request for "a different UI", an alternate/classic/flat language, or a non-Material look is a rewrite of the entire UI and the project has a stated policy against it in `DESIGN.md`. Specific complaints - a radius, a nav-bar dimension, one animation - are normal UI work and fair game.
- **A music home is mostly artwork shelves.** [scar] Two versions of Spotlight were built and thrown away, both on the premise that horizontal shelves are what make a home feel busy, so neither had any. Every real music app is mostly shelves; without them it does not read as a music app.
- **Two Homes share one data source.** Everything Spotlight shows comes from flows `HomeViewModel` already exposes. The moment one Home owns data the other does not, there are two to keep working and one falls behind.
- **PO tokens are not the fix for stream extraction.** [verified August 2026] NewPipe ships a complete BotGuard implementation that is dead code: its `PoTokenProviderImpl` returns null for Android and iOS, and those are the only two getters `YoutubeStreamExtractor` calls - `getWebClientPoToken` has zero call sites even at the commit NewPipe itself pins. Wiring `setPoTokenProvider` on v0.26.5 is a no-op. BotGuard cannot mint an ANDROID_VR token either; that needs DroidGuard. PipePipe gets tokens only by forking the extractor. The maintained Android-reel/visionOS chain works without attestation, which is why it is the primary path.
- **Backups copy stores rather than serializing models**, so a new setting rides along for free. A `@Serializable` mirror per repository reintroduces the search-index failure: add a setting, forget the second place, discover it on restore.
- **The rate-limit hold never gates playback.** Refusing locally turns a server-side throttle into an app that looks broken.
- **Search results are never filtered by the blocklist.** Searching is explicit intent; hiding a result someone just typed the name of is the app arguing with them.
- **Saved playlists are references, never copies.** Copying freezes someone else's playlist at the moment it was saved, which is the opposite of what saving one is for.
- **There is no master issue table.** Issue #174 was one and went stale within a day. Labels live on the issues.

## 6. Build, test, verify

```powershell
.\gradlew compileDebugKotlin     # fast compile check, no packaging
.\gradlew installDebug           # build + install (applicationId gets a .debug suffix)
.\gradlew testDebugUnitTest      # JVM unit tests
.\gradlew assembleRelease        # signing from local.properties, or KEYSTORE_PASSWORD / KEY_ALIAS / KEY_PASSWORD
```

Remember rule: **the ones that only build are yours to run; the ones that reach a device are not.** `compileDebugKotlin`, `testDebugUnitTest` and `assembleRelease` need no permission. `installDebug` does, because it wants a running device.

- **Tests.** A small JVM suite under `app/src/test/` covers pure logic only - parsers, formatters, the rate-limit hold. `testOptions { unitTests { isReturnDefaultValues = true } }` is set because `KLog` writes through `android.util.Log`, an unmocked stub that throws on every call in JVM tests; without it nothing in `data/` is testable. **That same flag silently breaks `org.json`** [scar]: `JSONObject` and `JSONArray` are stubbed in the same android.jar, so with default values they parse every input to nothing and a parser test fails with an empty result rather than an error - which is why the InnerTube parsers went untested for so long. `testImplementation(libs.json.unit.test)` puts a real `org.json` on the unit-test classpath ahead of the stub. Any new parser test depends on it being there. No instrumented tests worth running. Anything touching UI or the network is verified by compile plus a run on the emulator.
- **Emulator - the user's to run, not yours.** `emulator -avd Pixel_8_API36` (tools on PATH), then `adb wait-for-device`. Current SDK at `E:\Android\Sdk`. The debug build installs as `com.ivor.ivormusic.debug` and lives beside the release app rather than replacing its data, session and widgets - so resolve the launcher activity rather than assuming the package name. Kept here because it is what the user needs to type; anything only verifiable on a screen is handed back with what to look at.
- **Versions.** `versionCode` / `versionName` in `app/build.gradle.kts`. Dependency versions live only in `gradle/libs.versions.toml`.
- **minSdk is 30, and desugaring is load-bearing.** [scar] `isCoreLibraryDesugaringEnabled` plus `coreLibraryDesugaring(libs.desugar.jdk.libs.nio)` - it must be the `_nio` flavour. NewPipe calls Java 10/11 library APIs the platform only shipped in API 33 (`URLEncoder.encode(String, Charset)`, `URLDecoder.decode(String, Charset)`, `Collectors.toUnmodifiableList()`) and D8's built-in backports miss those three, so removing desugaring makes every search throw `NoSuchMethodError` on API 30-32 while compiling cleanly. Desugaring is not permission to ignore every `NewApi` finding: `InputStream.readNBytes` in the local-lyrics content-URI path was still an API-33 call and is now `LocalLyricsSource.readBounded`, an ordinary bounded read that works on API 30. Anything gated above 30 (dynamic color at 31, Live Updates at 36) needs a `Build.VERSION.SDK_INT` guard and a working fallback.

## 7. YouTube data layer (`data/YouTubeRepository.kt`, the heart of the app)

Two extraction mechanisms side by side: **NewPipe Extractor** for search, stream URLs and playlists (initialised once with `NewPipeDownloaderImpl`, which injects session cookies), and **raw InnerTube JSON over OkHttp** for what NewPipe cannot do - personalised feeds, watch history, engagement, account info. Parsing is manual `org.json` traversal with recursive helpers (`findObjectsByKey`, `findContinuationTokens`, `getRunText()`). No kotlinx-serialization for InnerTube responses.

### The probe-first workflow (follow exactly)

Never write or modify an InnerTube parser from memory or training data. Shapes drift and renderers get renamed wholesale (`commentRenderer` → `commentEntityPayload`, `videoRenderer` → `lockupViewModel`).

1. **Probe the live endpoint before touching Kotlin.** A gitignored `.probe/` helper exists: `py .probe/probe.py <endpoint> '<json body>'` (add `--music` for music.youtube.com). It reads the pinned client version live out of `YouTubeRepository.kt` and signs with the captured session, writing to `.probe/last_response.json`. **Never commit `.probe/`.** Otherwise write a throwaway script in the scratchpad (`py`, not `python`). Set `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` or emoji in responses crash the Windows console.
2. **For logged-in endpoints**, the session comes from the emulator's WebView jar (`adb exec-out run-as <pkg> cat app_webview/Default/Cookies`), sent as a `Cookie:` header and signed with `Authorization: SAPISIDHASH {ts}_{sha1("{ts} {SAPISID} {origin}")}` plus `Origin`, `X-Origin`, `X-Goog-AuthUser: 0`. **The hash is per-origin** - `music.youtube.com` and `www.youtube.com` need different ones. **An empty WebView jar does not mean signed out:** a session established through the app's paste-a-cookie path never opens a WebView and lives only in `yt_music_session.xml` (EncryptedSharedPreferences, keystore-bound, unreadable off-device). Check `shared_prefs/` first and fall back to the captured `.probe/Cookies.db`. Confirm a live session by `logged_in: 1` in the response tracking params, never by HTTP 200.
3. **Inspect shapes with a recursive key search, not by eyeballing.** Save the response, walk it with a `find_all(node, key)` helper, count candidate renderer keys, print one exemplar's key list and the exact paths to title/thumbnail/id. Only then write the parser.
4. **Write parsers the way the file already does:** `optJSONObject`/`optString` chains, `findObjectsByKey` for deep collection, `getRunText()` for text (handles `simpleText` and `runs`), `?.takeIf { it.isNotBlank() }` plus a fallback for every field, try/catch returning empty/null with a log. Note "verified <month year>" in the KDoc so staleness is visible.
5. **Client cheat sheet.** WEB (`webContext()`, `postWatchApi()`) for browse/next/engagement on www.youtube.com; WEB_REMIX (`fetchInternalApi()`) for music.youtube.com; NewPipe's Android-reel/visionOS chain for video VOD playback; ANDROID_VR (fallback IOS) only as the direct stream fallback and caption source.
6. **When an existing call starts failing**, log the HTTP code, the first ~200 chars of body, and `playabilityStatus.reason`. HTTP 400 on browse usually means the pinned client versions are too old - bump them. Empty `streamingData` with status OK usually means stale or missing `visitorData`. Do not loop retries; re-probe and compare shapes.
7. **Be frugal per user action.** One `/next` carries engagement, metadata, related videos and the comments token at once. Parse many features from one response (`getWatchNextData`) rather than adding a request per feature.
8. **Clean up write-probe side effects** (delete test comments) and never commit cookie dumps or response JSONs.

Known browse IDs [verified July 2026]: `FElibrary`, `FEplaylist_aggregation` (playlists as `lockupViewModel`s with `contentType: LOCKUP_CONTENT_TYPE_PLAYLIST`), `VL<playlistId>` (contents; `VLWL` Watch Later, `VLLL` Liked), `FEhistory`, `FEchannels`. Public `FEtrending` is dead (HTTP 400 since mid-2025); video feed order is personalised `FEwhat_to_watch` when logged in, then a taste-based mix from local watch history (`getTasteBasedVideos`), then a generic search cold-start.

### Client and identity

- **Client versions** (`WEB_REMIX_VERSION`, `WEB_VERSION`) are pinned constants that must be bumped periodically; YouTube rejects clients older than a few months. Keep `BROWSER_USER_AGENT` plausible against them - a Chrome version years older than the claimed InnerTube build is self-inconsistent.
- **Stream resolution is NewPipe-first.** Extractor v0.26.3 introduced the Android reel + visionOS workaround for SABR-only responses; Koda pins v0.26.5. The direct `ANDROID_VR` → `IOS` resolver is last-resort only and still supplies captions. Keep `uaForPlaybackUri()`'s NewPipe UA versions in step with an extractor bump.
- **A googlevideo 403 on the direct fallback is usually the `visitorData`, not the User-Agent.** [verified August 2026] GVS PO-Token enforcement reached `ANDROID_VR`, and IOS too; it can wall a progressive URL after an initial byte window (measured: first ~1.1 MiB served, then 403 for every byte past it, stable for a given token, roughly half of freshly minted tokens refused). The verdict is keyed on the token, not the video or client - which is why these clients cannot regain primary status merely because their `/player` succeeds. `refreshVisitorDataAfterPlaybackFailure()` is the recovery; a surface that plays direct googlevideo streams without wiring it has no way out of a bad visitor bucket.
- **`visitorData` belongs on every InnerTube call, not just `/player`.** [scar] It is minted, persisted, TTL'd (6h) and re-minted on the bot-check signal - and for a long time browse, next, search and engagement carried none of it, so each was a brand-new anonymous client and a session was hundreds of them from one address. `webContext()` and the browse helpers attach `cachedVisitorDataOrNull()` - a non-suspending read, because these helpers must not block on a mint, and an empty cache sends nothing, which is exactly the old behaviour - plus `X-Goog-Visitor-Id` and the `X-YouTube-Client-Name`/`-Version` headers a real WEB client always sends. **Sending it alongside account cookies is safe** [verified August 2026, live signed-in `FEsubscriptions`: identical `logged_in=1` and near-identical payload with and without].
- Minting is the cheap `youtubei/v1/visitor_id` endpoint, bootstrap-HTML scrape only as fallback, prefetched at both `VideoPlayerViewModel.init` and `MusicService.onCreate`.

### Signed-out behaviour

- **`fetchYouTubeBrowse` used to return an empty string the moment cookies were missing** [scar], so every public read built on it came back empty rather than failing, reading as broken content instead of a missing session - that is what made every video-mode playlist page say "No videos in this playlist" signed out. Public browse ids answer 200 anonymously [verified August 2026: `VL<playlistId>` returns the full item list with no cookies, no auth header, no visitorData], so account headers are conditional and the call is not. The consequence: **an account-scoped browse signed out returns a valid shell rather than an error**, so `FEplaylist_aggregation`, `FEhistory` and friends must gate on `isLoggedIn()` at their own call site.
- **A signed-out playlist browse returns `lockupViewModel`s where a signed-in one returns `playlistVideoRenderer`s** [verified August 2026], which is why `getPlaylistVideos` parses both and why the lockup branch is the normal path rather than the fallback it looks like. **NewPipe's playlist extractor only collects `playlistVideoRenderer`s**, so signed out it returns zero items and throws nothing - reaching for it as the signed-out path was the first fix attempted and produced a silently empty page with nothing in the log. It survives as `getPlaylistVideosAnonymous`, the last resort after the browse parses to nothing, precisely because it reads a different shape. Music playlists walk `browseMusic` and its continuation chain through one helper, `getBrowsePlaylistSongs`, for both session states - `browseMusic` and `fetchContinuation` attach account headers only when there is a session, and a public playlist pages to its end with none. A NewPipe continuation failure is incomplete even when page one returned exactly 100 songs, and must not block the authenticated path. Playlist rows preserve order and duplicates - the same video id can legitimately appear twice.

**A continuation answers in a different container than the page that spawned it, and music never learned the current one.** [scar] [verified August 2026 against a 982-track playlist] Page one puts its tracks in `musicPlaylistShelfRenderer.contents` - 100 rows plus a trailing `continuationItemRenderer` holding the next token. The continuation reply carries neither that shelf nor any `continuationContents.<x>Continuation`, the legacy containers `findRootContents` knew; it answers under `onResponseReceivedActions[0].appendContinuationItemsAction.continuationItems`, again 100 rows plus the next `continuationItemRenderer`. So the token was found correctly and every page after the first parsed to nothing, which capped every playlist at exactly 100 songs *and reported the load complete* - no retry, no fallback, nothing logged. `continuationItemsOrNull` (`data/InnerTubeContinuations.kt`, its own file so a JVM test can reach it) reads that shape, and `extractPlaylistContinuationToken` gained the matching scopes because page two onward has no shelf to scope to. **Its scoping is still load-bearing**: the same page carries a `sectionListRenderer.continuations` token whose reply is a `musicCarouselShelfRenderer` of related playlists, so a bare `findContinuationTokens` over the whole response follows the wrong chain. The video path (`extractVideoPlaylistContinuationToken`) already listed `appendContinuationItemsAction`; only music was left behind, which is why the reports were music-mode only.

### Being throttled

- **Throttling is a state the app holds, not a symptom it re-discovers** (`data/YouTubeRateLimit.kt`). **Only HTTP 429 arms it.** A googlevideo 403 is the PO-Token verdict on `visitorData` and already has a working recovery; routing it here would replace a remint with a five-minute sulk. An InnerTube 403 usually means "you may not read this". The hold gates **discretionary fan-out only** - the subscriptions feed, the avatar backfill, `UploadCheckWorker` - and never playback or anything a user is waiting on. `Retry-After` is honoured, clamped to 30 minutes, and a concurrent 429 can only lengthen an existing hold.
- **The subscriptions feed's "RSS, else browse" fallback must not answer a 429.** [scar] The fallback exists for channels that 404 the feed URL YouTube advertises in their own `channelMetadataRenderer.rssUrl`, and that is the only failure it is right for. A 429 is a verdict on the device: the browse will be refused too, and taking that branch for every channel turns a 10 MB refresh into a 200 MB one aimed at the server that just said stop. `fetchChannelFeedRss` returns `ChannelFeedResult` rather than a list - `NoFeed` and `Failed` escalate exactly as before, `RateLimited` stands the whole refresh down. [verified August 2026: a nonexistent channel id answers 404, so the escalation path is unchanged; feeds are served `public, max-age=900` with no ETag.]
- **The OkHttp disk cache is companion-level because it must be.** OkHttp's `Cache` is a DiskLruCache holding an exclusive lock on its directory, and this app builds a repository per ViewModel - several `Cache` objects on one directory is corruption, not contention. InnerTube calls are POSTs and are never cached, so it can only serve a stale *feed*; an explicit pull-to-refresh passes `forceFresh` and revalidates, because a refresh that visibly changes nothing is worse than the traffic it saves.

### Response shapes

- **Comments** use `commentEntityPayload`: entities in `frameworkUpdates.entityBatchUpdate.mutations`, ordering from `commentThreadRenderer`s in `onResponseReceivedEndpoints`. Legacy `commentRenderer` no longer exists.
- **Feed and related items** are `lockupViewModel`s parsed by `parseLockupViewModel`; `videoRenderer` is legacy but still handled.
- **A collab video names no owner at all.** [verified September 2026, signed out] YouTube's collaborations feature puts up to five channels on one upload, and its `videoOwnerRenderer` then carries **no** `title`, `thumbnail`, `subscriberCountText` or `navigationEndpoint.browseEndpoint` - only an `attributedTitle` ("KSI and 2 more", already localized), an `avatarStack` of every collaborator, and a `navigationEndpoint` that is a `showDialogCommand`. The `subscribeButtonRenderer` carries no `channelId` either. So before `parseCollaborators` the watch page had no channel to open and nothing to subscribe to; the collaborators come free inside that command's `dialogViewModel.customContent.listViewModel.listItems[]` (name, `browseEndpoint.browseId`, `@handle • N subscribers` in `subtitle`, avatar in `leadingAccessory`, `CHECK_CIRCLE_FILLED` in `attachmentRuns` for verified), so listing them costs no request. The dialog is reached structurally, never by matching its "Collaborators" headline, which is localized. Feed lockups carry the same dialog under `lockupMetadataViewModel.image.avatarStackViewModel`. Subtitle text arrives wrapped in bidi isolates (`BIDI_CONTROL_CHARS`) that must come off before it is split.
- **Chapters** live in the `/next` decorated player bar: `multiMarkersPlayerBarRenderer.markersMap` keyed `DESCRIPTION_CHAPTERS` or `AUTO_CHAPTERS`, each a list of `chapterRenderer { title, timeRangeStartMillis, thumbnail }`; document order is chronological. [verified July 2026]
- **Captions** come from the **ANDROID_VR** `/player` call (IOS fallback), never WEB: `captions.playerCaptionsTracklistRenderer.captionTracks[]`, each with `baseUrl`, `languageCode`, `name`, and `kind == "asr"` / `vssId` starting `a.` for auto-generated. [scar] A WEB `/player` without account cookies answers UNPLAYABLE with no captions block at all, which gave every signed-out user an empty CC menu; the native clients return the full tracklist signed out. `parseCaptionTracks` runs on every `/player` response and `runPlayerClientChain` caches per video id (30 min TTL, LRU 16), so a lazy CC tap normally costs no network. [verified July 2026]
- **Timedtext `baseUrl`s must have their format replaced, not appended.** [scar] ANDROID_VR hands back URLs already carrying `&fmt=srv3` and the endpoint honours the *first* `fmt`, so `"$baseUrl&fmt=vtt"` silently returns srv3 XML under a `text/vtt` MIME type and the subtitle load fails. `CaptionTrack.vttUrl` strips `&fmt=`/`&tlang=` then appends. Do not "simplify" it back.

## 8. Playback

Two entirely separate pipelines. **Music**: `MusicService` (Media3 `MediaLibraryService`) plus `PlayerViewModel` over a `MediaController` - background playback, notifications, queue. **Video**: `VideoPlayerViewModel` owns its own `ExoPlayer` directly, no service - DASH or merged progressive, PiP in `VideoPlayerOverlay`.

**Music modes are service-owned and durable.** Shuffle uses one persisted seed and the same explicit `ShuffleOrder` on both crossfade players, so swapping players cannot silently generate a new order and replay songs. Shuffle, repeat and an active sleep timer survive process recreation; end-of-track sleep applies to both players while duration sleep stores a wall-clock deadline. Sessions checkpoint every 15 seconds and on backgrounding. Restoring a music placeholder must preserve its saved seek when the real stream replaces it. Video sessions restore queue, item and position but deliberately exclude live and completed videos.

**Music stream resolution is a single-flight, but no resolution work may run inside a `ConcurrentHashMap.compute*` callback.** [scar] A download, valid in-memory URI or fully cached song can finish before `getOrStartResolution` has even returned. The old `computeIfAbsent` mapping function registered `invokeOnCompletion { map.remove(id) }`; when that fast result had already completed, coroutine registration invoked the cleanup synchronously from inside the map computation and Android's `ConcurrentHashMap` threw `IllegalStateException: Recursive update` on the main thread. `DeferredSingleFlight` publishes a lazy deferred with `putIfAbsent`, registers conditional cleanup, and only then starts it. Preserve that order, and preserve `remove(key, deferred)`: an older forgotten resolution must not remove its replacement.

**A notification permission check is not permission to post later.** [scar] Android can revoke `POST_NOTIFICATIONS` between `checkSelfPermission` / `areNotificationsEnabled()` and the binder call. Download completion/failure, download foreground updates and the optional playback Live Update all catch `SecurityException` at `notify()`; a cosmetic notification must never crash playback or the transfer service. The initial foreground promotion is separate and already catches platform refusal, because a service started with `startForegroundService` must stop promptly if promotion fails.

**Single-button wired headsets are resolved in `MusicService`, and only `KEYCODE_HEADSETHOOK` is intercepted.** [verified August 2026 against the then-pinned Media3 1.5 bytecode; Koda keeps the resolution app-owned on Media3 1.11] Media3 maps one press to Play/Pause and two to Next, but treats a third press as the start of another single press, producing Next followed by a delayed Play/Pause. `HeadsetButtonSequence` preserves single and double press and adds triple press as Previous; double press necessarily settles after the same multi-press window so a third press can still win. Triple Previous always changes tracks rather than applying the ordinary three-second restart rule. Explicit Play/Pause, Next and Previous keys, notification controls, Android Auto and controller commands stay on Media3's existing paths.

**All googlevideo media goes through bounded ranged requests.** [measured July 2026: 32 KB/s open-ended versus 5-22 MB/s bounded on the same URL] googlevideo paces open-ended progressive requests to roughly the media bitrate, which reads as "slow loading on a good network". Playback uses `data/ChunkedStreamDataSource` (10 MB chunks plus per-URL UA, wired via `CacheManager.createPerClientHttpFactory()` and the video VMs' `streamDataSourceFactory`); `DownloadRepository.downloadStream` runs its own ranged loop. `MusicService.prefetchUpcomingSongs` additionally pre-caches the first 512 KB of the next 3 queue songs (`warmStreamCache`) so skips start from disk. **Music and video use different caches.** [scar] The old shared size-bounded `SimpleCache` let one high-bitrate video consume a user's entire music cache limit and evict songs, while a 4K video larger than the limit continually evicted its own beginning. Music keeps the adjustable LRU and is the only cache shown in Settings and Ready offline. Video and Shorts use an uncapped transient `SimpleCache` that clears five minutes after the last video surface closes; a full disk degrades to direct playback through `FLAG_IGNORE_CACHE_ON_ERROR`. Old `video-playback:` and opaque video entries are removed from the music LRU on process start. Progressive VOD keeps stable `video-playback:<videoId>:<role>:<itag>` keys, with separate video/audio/muxed roles so split sources and qualities cannot mix bytes. Local Only is enforced in the upstream `ChunkedStreamDataSource`, below both cache pipelines, so cached spans and device files remain readable while the first cache miss is refused.

**Video and Shorts players are lazy.** Their ViewModels still exist at Home scope because overlays, route hand-offs and restored sessions address them from several tabs, but an ExoPlayer is not built until a video is opened or a saved video session is restored. Closing video cancels its 500ms progress poll. Shorts resolves two upcoming stream ladders rather than five and warms actual progressive bytes only for the immediate next item (smaller on metered networks); live/adaptive sources are never range-warmed. MusicService no longer downloads recommendations and playlists merely because the app bound its controller—Android Auto browse performs its existing cold fetch or stale-while-revalidate when a client actually asks.

**Seek latency is set by the load control and the seek parameters, not by the disk cache.** [scar] The seek bar's pale segment is `player.bufferedPosition` - ExoPlayer's in-memory sample queue - so `DefaultLoadControl` *is* the RAM cache for video, and the disk cache only backs its misses. Two defaults made a scrub stall even when every byte was already in RAM. `bufferForPlaybackAfterRebufferMs` was 2.5s: a seek out of the buffered region counts as a rebuffer, so the first frame was withheld until 2.5s of media had been queued regardless of where the bytes came from. And ExoPlayer seeks exactly by default, decoding from the preceding sync sample and discarding every frame up to the target - hundreds of them on a 1080p60 multi-second GOP, again paid on cache hits and network fetches alike. Scrub-bar drags and the 10s steps now pass `SeekParameters.CLOSEST_SYNC` through `seekPlayerTo`, which renders the nearest keyframe; chapter starts, comment timestamps and every session or quality-switch restore pass `precise = true` and keep `EXACT`, because those address a specific moment and landing half a GOP away is wrong. The back buffer is 45s rather than 15s, since backwards is the common scrub direction and 15s sat inside one drag. The 96MB allocator ceiling is shared by a split pair's video and audio sources and by that back buffer, so it - not `maxBufferMs` - is usually what bounds how much of a scrub is served from memory.

**Quality.** `VideoQuality(resolution, url, format, isDASH, audioUrl)` where `resolution` is a YouTube label ("1080p60", "720p"). Both `getVideoQualitiesFromNewPipe` and `parseQualitiesFromStreamingData` return highest-first ladders with 60fps before 30fps. Generated NewPipe manifest *content* (`Stream.isUrl == false`) must never reach a Media3 URI source. Starting quality comes from per-network settings (`ThemePreferences.getDefaultVideoQuality()`, a fresh read picking Wi-Fi or mobile via `isActiveNetworkMetered`) through `pickDefaultQuality`: best label at or below target height, else lowest. Music resolution honours per-network music quality the same way (`currentMusicQuality`: high/normal/low). **HDR is opt-in** (`prefer_hdr_video`, default off). NewPipe v0.26.5's itag table ends before YouTube's HDR itags 330-337, so it makes the visionOS request and then drops every HDR rendition from its Stream models; when the setting is on, `resolveVideoStreamResult` runs the raw visionOS `/player` in parallel and merges back only the HDR entries [verified September 2026: itags 330-337, VP9.2, unciphered URLs, signed out]. HDR and SDR coexist at one label - `VideoQuality.dynamicRange` is part of the dedupe and selection identity, never a variant to collapse. The mini player is a TextureView and cannot present HDR, so minimising drops to the matching SDR rung and expanding restores it. Video downloads pick the best MP4 adaptive pair at or below the `VideoDownloadSheet` choice, the request carrying the label so retries keep it.

**Video loads in two phases** (`VideoPlayerViewModel.startVideo`, which `playVideo` and the queue both funnel into). Phase 1 calls `getVideoStreamQualities()` - stream URLs only, 15s timeout - and starts playback, deliberately through one NewPipe `fetchPage()`. Phase 2 runs `getWatchNextData()` in parallel: a single `/next` parsed into engagement, enriched metadata and related videos. Do not add another per-video extraction or extra `/next` calls there. The video ExoPlayer uses a tuned `DefaultLoadControl`, as `MusicService` does; see the seek-latency paragraph below, because those numbers decide how a scrub feels rather than only how playback starts.

**Stream resolution is shared across video surfaces.** `VideoStreamResolutionCache` single-flights NewPipe's blocking `fetchPage()` and keeps at most 16 successful ladders, expiring each at the earliest signed video/audio URL minus five minutes (15 minutes for a URL with no readable expiry). This is why opening the download sheet for the video already playing, or moving between a Short and its watch page, does not extract it again. Empty results are never cached. A source recovery invalidates that video's ladder before retrying; a visitorData remint or profile switch clears every ladder, because returning an old signed URL there would make recovery a no-op. The many `YouTubeRepository` instances retain separate cookie jars and Local Only interceptors but share one bounded OkHttp dispatcher and connection pool so they reuse threads and sockets.

**MusicService's session caches are bounded.** Resolved music URLs are an access-ordered 128-entry map and the successful warm bookkeeping keeps 256 ids; both may span hours of continuous listening, so an unbounded collection is a leak even though each entry is small. Evicting a warmed id is harmless because `CacheWriter` skips bytes already on disk. Live Update artwork ids are in-flight markers, removed when each load finishes, rather than a permanent record of every cover seen during the service lifetime.

**Mini-to-expanded uses a lightweight reveal curtain**, not animated height/padding or transforms on the full-screen player. Both alternatives make the embedded video surface expensive - layout remeasures it every frame, scaling can overwhelm the emulator compositor and lower-end GPUs. Keep the mini-player tap/swipe gestures; animate only the small mini bar and the plain-color reveal layer.

**A video opened from a playlist carries the playlist with it** (`data/VideoQueue.kt`). [scar] Without one, tapping the third entry played that video and then auto-played the first *related* video - a recommendation, almost never the fourth entry. `playQueue` is the only thing that establishes a queue; `playVideo` clears it, because a related video, a channel row or a search result all mean "done with that playlist", and `startVideo` is the shared private worker so retrying a failed video does not count as leaving. **The queue is addressed by index, never by `videoId`** - a playlist may list the same video twice, which is also why every jump forces a restart rather than letting an id check swallow it. It is a snapshot at tap time, because `HomeViewModel.playlistVideos` is overwritten by the next playlist opened. On `STATE_ENDED` the queue beats the related video outright and advances **even in PiP**. An unplayable entry is stepped over after both retry budgets are spent, capped at `MAX_QUEUE_ERROR_SKIPS` and reset on the first video reaching `STATE_READY`, so one dead entry cannot end the run and a dead network cannot burn the whole playlist. UI: a "Playing from" card, `ui/video/VideoQueueSheet.kt` (hosted by `VideoPlayerContent`, so fullscreen reaches it), next/previous flanking play/pause in both chromes, and a next button on the mini bar. Up Next relabels to "Related videos" while a queue runs.

**Chromecast was removed in full and is being rebuilt from scratch.** The old implementation did not work and was carrying `media3-cast`, `play-services-cast` and `androidx-mediarouter` plus a `CastPlayer`/`ExoPlayer` split that reached into both playback pipelines - `VideoPlayerViewModel.activePlayer()`, `MusicService`'s receiver queue, per-style cast buttons, and a receiver-safe quality policy that narrowed the quality sheet. All of it is gone, including the manifest `OPTIONS_PROVIDER_CLASS_NAME` meta-data, so a rebuild starts from a clean sheet rather than inheriting that shape. Two things survive because they were never really about Cast: `deduplicateVideoQualityVariants` still keeps one muxed and one split entry per label, which download selection needs, and `localVideoQualityOptions` (now `ui/video/VideoQualitySelection.kt`) still projects one playback entry per visible label. Do not reintroduce a `Player`-typed indirection for the local player alone - `_exoPlayer` is the only player there is now, and the old alias is exactly what made cast-only no-ops hard to see.

**Player extras.** **Captions** are fetched and parsed independently into `VttCue`s, then drawn by Koda's overlay instead of being merged into the local Media3 source. Switching captions therefore never re-prepares playback or discards the sample buffer; malformed tracks fail to an empty overlay rather than a source error. **Every `PlayerView` Koda draws captions over must call `disableBuiltInSubtitles()`.** [scar] `PlayerView` renders cues into its own `SubtitleView`, and because YouTube captions never reach the Media3 source that view had nothing to draw - so the duplication stayed invisible until device videos arrived. A file's *embedded* subtitles are real cues on the player, and both renderers then drew the same line at once, Koda's in the user's chosen size, colour and background and PlayerView's in the platform's caption style. **Media3 is pinned as one version catalog family** (currently 1.11.0); `LiveUpdateMediaNotificationProvider` delegates the library's notification-channel metadata as well as notification creation so custom progress updates do not fork the channel contract. **Chapters** render as seek-bar ticks, a current-chapter chip and a sheet. **Hold-to-2x** is a long-press in `PlayerGestureSurface` restoring the prior speed on release. **Share** fires `ACTION_SEND` with `youtube.com/watch?v=<id>`; playlists share `youtube.com/playlist?list=` or the music equivalent, albums `/browse/`, and it is hidden for local playlists and the private WL/LL feeds.

**Lyrics layout is owned by `SyncedLyricsView`, not by each player style.** Every style gives it the full available pane; the shared view chooses one responsive gutter, line spacing and vertical runway. Do not put another lyric-only horizontal padding wrapper around it. [scar] The active line used to be enlarged with a post-layout `scale`, so its measured bounds stayed small while the drawing grew outside them; large app or system text scale then clipped words against the pane and adjacent lines. Emphasis now comes from measured typography and weight. Karaoke words measure against the actual pane, soft-wrap even one unbroken token, reserve side/top drawing insets for glyph bearings and motion, and preserve the displayed line as authoritative when provider timing omits final punctuation. Auto-scroll uses each wrapped row's measured centre rather than assuming a fixed-height line.

### SponsorBlock

Crowd-sourced segment skipping, **video mode only** and off until switched on (`data/SponsorBlock.kt`, `data/SponsorBlockRepository.kt`, `ui/settings/SponsorBlockSettings.kt`, `ui/video/SponsorBlockChip.kt`).

**The video id never leaves the device.** The request carries the first four hex characters of its SHA-256 and the server answers with every video sharing that prefix, which the client filters locally. The plain `?videoID=` form of the same endpoint exists and is easier; using it would hand a third party a complete record of what every user watches. This is also the only third-party service the app contacts at all, which is why the feature is opt-in and the settings page names the host before the switch rather than after it.

**Three states per category, not one switch.** [judgement] A sponsor read is something nearly everyone wants gone; an intro or an off-topic section in a music video is something plenty of people want kept. `SegmentAction` is `SKIP`/`MANUAL`/`IGNORE`, defaulting to skip for sponsor, self-promo and interaction reminders and ignore for the rest - matching SponsorBlock's own defaults. `IGNORE` is enforced at the *request*, not after it: `activeCategories` decides what is asked for, so an ignored category is never received.

**`SponsorCategory.apiName` is the wire format and is frozen**, the same way a persisted enum constant is - the encoded preference stores it, so renaming one resets that category to its default for every existing user. `encodeSegmentActions`/`decodeSegmentActions` are one preference key rather than eight, and tolerate unknown names and unknown actions in both directions so an older and a newer build cannot poison each other's stored value.

**The skip decision rides the existing 500ms progress poll** rather than adding a timer, so a skip can land up to one tick late; submitted segments carry their own padding, and a second loop was not worth frame accuracy. No scrubbing guard is needed because `PlayerSeekBar` commits on release, so the player's position does not move mid-drag. **Overlapping segments resolve to the one ending latest** (`segmentAt`), because a nested self-promo inside a sponsor read would otherwise skip to the nearer end, land back inside the outer segment and skip again - one stutter instead of one skip.

**A skipped segment goes into an ignore set keyed by submission UUID.** Undo seeks back and leaves it there: undoing means the viewer wants to watch that part, so asking again on the next tick is the bug. The set is per video and cleared with the rest of the state, since the UUIDs are unique per video and nothing will read them again.

**The chip is deliberately outside the control-visibility gate.** A skip is the one thing that happens without being asked for, so an undo reachable only when the chrome happens to be up is not reachable at the moment it is needed. **Live videos are excluded** - there is no fixed timeline to key a segment against - and only `actionType: skip` is acted on: `full` would skip to the end of the video, `poi` is a point rather than a range, and `mute` needs volume control this does not implement.

**Read-only, on purpose.** Submitting and voting need a persisted anonymous user id, a marking UI and write endpoints; that is its own feature and belongs in its own issue rather than riding along with skipping.

### Live streams

A live broadcast is not a separate content type. It is a normal video whose `/player` response carries an HLS manifest, and everything follows from that.

**Detection is the formats, not the manifest.** [scar] `streamingData.hlsManifestUrl` is present on live responses and absent on VODs *for ANDROID_VR* [verified August 2026], and that client-specific fact was written down as though it were universal. It is not: [verified September 2026] visionOS and IOS return `hlsManifestUrl` on every ordinary VOD. Gating on the key alone therefore made the visionOS HDR augmentation classify every video as live, return an all-SDR HLS ladder, and reduce the entire HDR feature to a silent no-op - green unit tests included, because they built a `streamingData` without the key. The discriminator is whether the renditions describe whole files: a VOD format declares `contentLength` and an ordinary ranged URL, a live one is a segment endpoint carrying neither. `parseDirectVideoQualities` returns the HLS ladder only when the manifest is present *and* no rendition is a VOD file, and stamps `VideoQuality.isLive`; `VideoPlayerViewModel` reads `_isLive` off the quality list rather than paying for a separate call. [scar] Live is the one case where `adaptiveFormats` progressive URLs are unusable - they are segment endpoints (`live=1`, `noclen=1`), so an unbounded GET returns one ~2s segment and a ranged GET blocks until timeout. That was the "live video opens but never plays" failure.

**The quality ladder is labels only.** Every rendition lives in the one manifest, so all entries carry the same URL and picking one calls `applyLiveQualityCap` (`setMaxVideoSize` plus `setForceHighestSupportedBitrate`) rather than swapping the media source - quality changes cost no re-prepare and no rebuffer, which matters more on live than anywhere. The cap clears on the next `playVideo`, because track selection outlives media items and a cap picked on a stream would silently limit the next video.

**Live chat** (`getLiveChatSession` → `pollLiveChat`, `ui/video/LiveChatPanel.kt`). The continuation arrives free with the Phase 2 `/next` (`parseLiveChatContinuation`); polling starts only once chat is on screen. The server's interval is honoured but clamped to `LIVE_CHAT_MIN_WINDOW_MS`/`MAX` (a misparse must not become a hot loop), the backlog caps at `MAX_LIVE_CHAT_MESSAGES` (250, matching YouTube's own `maxItemsToDisplay`), and three consecutive failed polls give up. Sending echoes the accepted message back so it appears without waiting a poll; rejections (slow mode, word filter, ban) surface through `onFailure` so the composer restores the text. Super Chat colors come from YouTube and are the documented exception to the color rule. A finished broadcast exposes its replay chat under the same key; nothing consumes that today.

`LiveChatPanel` has three dresses and the `compact` flag selects only between the first two: default is an opaque `surfaceContainer` sheet over the info area (portrait); `compact = true` is a translucent column docked right of the video (landscape); `LiveChatOverlay` is a *separate* composable in the same file, a read-only ticker on a gradient for the full-bleed vertical player, reusing the message rows but passing `authorColorOverride` because the role tints are not guaranteed to carry contrast against video. Sending, scroll-back and the jump-to-latest pill stay with the full panel.

**Vertical live** is an ordinary broadcast encoded 9:16 - there is no "Shorts live" entity. [verified August 2026: `/shorts/<id>` resolves back to `/watch?v=`, its `/next` carries no `reelPlayerOverlayRenderer`, and five pages of `reel/reel_watch_sequence` returned zero live items.] **Orientation is the only signal**, so `VideoQuality.isPortrait` is derived at parse time from the largest dimensioned format on both paths; reading it from `onVideoSizeChanged` instead is too late and makes the layout snap after the first frame, though that remains the backstop. `isLive && isPortraitVideo` selects `VerticalLivePlayerContent` - full-bleed, chat ticker over video, controls on a timer but top chrome always up, immersive on open, `CloseFullscreen` dropping to the standard watch page and `StayCurrentPortrait` returning, the choice resetting per video. Fill-vs-fit is conditional: zoom-to-fill past `MAX_ACCEPTABLE_CROP` (25%) letterboxes instead, because "vertical" also covers 4:5 and 1:1 streams that would lose their top and bottom. **Landscape is the good case for 9:16**: the space beside the video is chat-shaped, so rotating auto-opens the docked column and `FullscreenPlayerContent`'s `videoEndPadding` slides the video clear (portrait sources only - shrinking a 16:9 video to dodge an overlay sitting on letterbox bars loses more than it gains).

**Portrait fullscreen has its own bottom bar, and the flanking readout was the problem.** `compactChrome` already moved the top-bar actions onto a line of their own; the same window has no width for `0:20 [bar] 0:46` either - two labels plus their gaps take roughly two fifths of a phone's short edge, leaving the track too short to scrub accurately and pushing the total hard against its end. In compact the readout is one `0:20 / 0:46` on a line above a full-width seek bar, sharing that line with the chapter chip or the live pill, and the bar stands further off the bottom edge because fullscreen hides the system bars, so `WindowInsets.navigationBars` reads zero and the row would otherwise sit under the gesture bar. Anything floating over the frame - captions, the SponsorBlock chip, timed comments - measures its clearance from `FULLSCREEN_COMPACT_BOTTOM_BAR` rather than repeating a literal, so the four cannot drift apart. Landscape keeps the bar it always had.

**Comments are hidden entirely on live videos** - the entry row, the timed-comments button in both chromes, the overlay, and the fetch behind it. Live chat is the conversation; a running broadcast's comment section is usually empty or disabled, and offering both sent people to the dead one. An open comments sheet closes when a live stream starts, since the sheet outlives the video it was opened on.

**A live item in the Shorts feed is handed off, not approximated:** `ShortsPlayerViewModel` emits `liveHandoff` and closes itself, and `MainActivity` reopens it in the video player. Emit *before* `close()` - it cancels the very job the emit runs in.

## 9. Navigation and screens

`MainActivity` hosts a `NavHost` (`onboarding` → `home`, plus `settings`, `downloads`, `stats`, `update`, and the channel route). The `home` route contains its own tab system - `AnimatedContent` plus an inline `HorizontalFloatingToolbar` built in `HomeScreen.kt`, not a separate nav-bar component - rather than nav routes. The expressive toolbar uses Material 3's own `exitAlwaysScrollBehavior(FloatingToolbarExitDirection.Bottom)` at the Home shell: every tab's nested scroll hides it downward and reverse scroll returns it, while the optional standard `NavigationBar` remains pinned. Do not replace that with list-index polling or a hand-rolled offset. A global `videoMode` toggle swaps the Home tab between music content and `VideoHomeContent`, and tab 2 between Library and video history. Both players are **overlays above the NavHost**, driven by their ViewModels' `isExpanded` state, which is why a NavHost destination like the channel screen needs them to step aside.

**Search history follows the field across modes.** `SearchScreen` uses the same `SearchHistoryRepository` in music and video mode: focusing an empty field shows the recent-query surface, and clearing focus returns to the mode's ordinary empty-query content. Video's empty state is Trending only; do not re-add hard-coded Explore category chips, which duplicate ordinary queries and hide the user's own history.

**Classic Home needs three usable recommendations, not merely a non-empty parser result.** Its organic hero addresses indices 0, 1 and 2, so accepting one malformed or partial `FEmusic_home` row leaves the signature three-artwork layout visibly broken. `usableHomeRecommendations` removes blank/placeholder titles and duplicate ids; `getRecommendations` keeps valid primary rows, then fills from Liked Music and finally a generic search until the surface has enough. `HomeRecommendationCache` stores at most 30 metadata rows per profile for seven days, renders them immediately while a refresh runs, and is cleared on logout; an empty/error response never overwrites it. It is a cache, not backed-up user data. No InnerTube shape was changed for this repair: a signed-in live response could not be probed without a device session, so the existing parser was left alone rather than edited from inference.

**Two music Homes, the second opt-in.** `spotlight_home` (off by default) swaps tab 0's music content from `YourMixContent` to `SpotlightHomeContent` - shortcut grid, paged quick picks, artwork shelves - chosen in onboarding's Look and feel page or Settings → Appearance → Home. It is a third branch in the same `when` the video toggle already uses, so the tab system, overlays and nav bar are untouched. A boolean rather than an enum on purpose: no third Home is planned. `isAutoMix` drops YouTube's machine-made mixes; nothing marks a playlist as generated, so the only signal is the title, and patterns are anchored on the whole name so a user's own "Late night mixtape" survives.

**Opening a Library sub-screen from outside Library is a hand-off, not a navigation.** `LibraryContent` owns playlist and artist detail in its own state, so callers pass `initialArtist` / `initialPlaylist` and clear them through the matching `onInitial…Consumed` callback as the tab renders. Without the clear, returning to Library re-opens whatever was last handed over. The player uses the artist half; Spotlight the playlist half.

### Device videos

The video Library's "On this device" entry (`ui/video/DeviceVideosPage.kt`, `data/LocalVideoRepository.kt`) reads MediaStore, groups by bucket into folder cards, and plays the files through the ordinary video player.

**Playback reuses the download path exactly.** `LocalPlaybackSource` generalises what `playDownloadedVideos` already had, so `_isLocalPlayback` still means "ExoPlayer is reading a file on this device" and everything gated on it - no `/next`, no YouTube playback report, no caption fetch, no HDR downgrade aimed at saving bandwidth that is not being spent - covers gallery files for free. A device video's id carries the `device:` prefix (`LocalVideo.playbackId`) because it travels through fields typed for YouTube ids; nothing may build a watch URL or an InnerTube request from one.

**Koda's own watch history is the one thing local playback does write.** `recordLocalWatch` applies the same rules the online path does - ten seconds of actual playback, a fresh `isSaveVideoHistoryEnabled` read - and stops there: nothing is reported to YouTube, because a device file is nobody's upload. Profile scope and incognito are enforced inside `VideoHistoryRepository.addVideo`, which is exactly why that gate lives in the store rather than at each call site. **The `device:` id is deliberately reversible** (`LocalVideo.uriFor`): history stores a `VideoItem` and nothing else, so replaying an entry and drawing its frame both have to get back to the file from the id alone - which is also why `playVideo` routes a device id to local playback itself instead of leaving each of the surfaces that open a video to remember. An externally opened one-off URI gets an `external:` id rather than a device one and is **not** recorded, since the read grant dies with the task and the row would be a dead link.

**Koda appears in "Open with" for video files, and hands files back out the same way.** The manifest claims `ACTION_VIEW` on `video/*` over the `content` and `file` schemes plus `ACTION_SEND` for a share; both are re-checked at handling time (`Intent.externalVideoUri`), because the filters match by mime type and a chooser can pass something else. `MainActivity.takeSharedLink` checks for a file *before* the link path - an "open with" puts the video in the same `data` field a YouTube link uses, and the link path would have called it "no YouTube link found". A URI that resolves back to a MediaStore row (`LocalVideo.playbackIdFor`) is treated as an ordinary device video, id and all. **Koda offers no delete**, and `openVideoWithExternalApp` is why it does not need one: the system chooser over `ACTION_VIEW` reaches the gallery or file manager, which already has the system confirmation and the user's own trash behind it.

**Quality and HDR are read back from the decoder, not from MediaStore.** The provider records dimensions inconsistently and says nothing about dynamic range, so the row starts as a placeholder and `applyLocalVideoFormat` renames it from the selected video track on the first `onTracksChanged`. HDR10 and HLG come from the track's transfer function and Dolby Vision from its codec - `VideoDynamicRange.DOLBY_VISION` exists only for this path, since YouTube never serves it but phone cameras record it constantly.

**Embedded audio and subtitle tracks are selectable** (`data/MediaTrackLabels.kt`, `publishSelectableTracks`). Overrides resolve against the player's live `Tracks` rather than a remembered group, because a track list belongs to the media item that produced it. Three rules worth keeping: a track the device cannot decode is left out rather than offered and then producing silence; the audio section appears only above one track, since one is not a choice; and subtitles open *off* unless captions were left on, enforced by disabling the track type - clearing the override alone lets the selector re-pick a container's default-flagged track, so subtitles the user just switched off come straight back.

**Thumbnails go through a small Coil fetcher, deliberately** (`data/LocalVideoThumbnail.kt`). `coil-video`'s decoder works from an `ImageSource`, meaning Coil fetches the file first - copying a multi-gigabyte film into the cache to draw a 200dp card. `ContentResolver.loadThumbnail` serves MediaStore's own pre-generated frame instead, with one scaled keyframe decode as the fallback for files the system scanner could not open. It needs a `Keyer` as well as a `Fetcher`: a request whose key is null skips the memory cache entirely.

**Access is asked for from the Library, not through a setting**, which is what keeps a permission dialog away from anyone who never opens the section - the same reasoning as the `load_local_songs` scar. Android 14's partial grant is a first-class state (`LocalVideoAccess.PARTIAL`): `READ_MEDIA_VISUAL_USER_SELECTED` is declared so the picker offers "Select videos" at all, the chosen files are shown with a way to widen the selection, and a wall over content the user has already shared would be the wrong answer. **Local Only mode hosts `DeviceVideosScreen` directly** in place of the notice that used to stand there, which is why the folder step lives in that composable rather than in the Library's page enum.

### Three kinds of playlist

Not interchangeable, in either mode. **Local** (`PlaylistRepository`, songs embedded, fully editable), **the account's own** (InnerTube, editable through it), and **saved** (`data/SavedPlaylistsRepository.kt`) - somebody else's, kept as a reference (id, url, title, author, artwork, count) and re-fetched live on every open, never copied. `HomeViewModel.userPlaylists` merges all three and `savedPlaylistIds` tells the third apart, deliberately excluding anything the account already owns. **That distinction is load-bearing** [scar]: a saved playlist's id starts with `PL` like any other, so without it the UI offers Rename, Delete and track editing on a playlist the user has no rights to, and those writes fail at the endpoint after the UI has already moved. Saved playlists never enter the add-to-playlist sheet, because you cannot add tracks to someone else's playlist. **A `PL` prefix says an id is a real YouTube playlist, not that it is yours** - both detail pages ask whether the library actually holds the playlist rather than reading the prefix.

**Video mode got its local kind last** (`data/LocalVideoPlaylistsRepository.kt`, videos embedded, one JSON file per playlist under `filesDir/video_playlists`). [scar] Until it existed, `videoPlaylists` was the account's list alone, so signed out the save sheet listed nothing, every long-press routed to a sign-in wall, and the pinned Watch Later row posted to an endpoint that answers 200 without a session and does nothing - the sheet reported a save that had not happened. Both `HomeViewModel.videoPlaylists` and `VideoPlayerViewModel.videoPlaylists` are now `combine(local, account)` with local first, and **the routing decision lives in `addVideoToPlaylist` rather than at the six surfaces that open the sheet**: a local id, or `"WL"` while signed out (resolving to a device Watch Later created on first use), or the account. The `localvp_` prefix exists precisely because that one id string reaches `addToYouTubePlaylist`, the playlist browse, the share-URL builder and the saved-playlist filter, each of which must branch. **Nothing may assume a `VideoPlaylist.playlistId` addresses YouTube.** A local playlist is a copy with no upstream, which is what separates it from a saved one, so `loadPlaylistVideos` serves it straight from the store.

**The saved store is one library across both modes.** Video mode saves into the same list and reads it back through `SavedPlaylist.toVideoPlaylist()`, so a playlist kept from video search is in the music Library grid too. A YouTube playlist id is the same id whichever page found it, and a per-mode store would make "saved" mean two things and let one id be saved twice. `getPlaylist(id)` resolves any playlist id through `https://www.youtube.com/playlist?list=`, which is why `SavedPlaylist.url` is stored in that canonical form. Albums cross over: a video-mode open of an MPRE id resolves through `loadPlaylistVideos`'s album branch rather than the playlist call a browse id cannot answer, and their share link is the `/browse/` form. Saved rows **render signed out**, which is why the login card sits underneath the list rather than replacing it.

**Playlist download inventory has two different counts and must name both.** A playlist is an ordered list of entries and may contain the same video id several times; offline storage is keyed by that id and correctly downloads one reusable file. Already-downloaded ids likewise reduce new transfer work without reducing the playlist. `MusicPlaylistDownloadAction` therefore labels its header action with the full playlist row count, while `PlaylistDownloadSheet` separately reports already-offline, repeated-entry and remaining unique-file counts. Never surface `distinctBy(id).size` as if it were the playlist's song count.

**Device albums follow tag order, not the library query order.** `SongRepository` reads TRACK, CD_TRACK_NUMBER and DISC_NUMBER and stores normalized positive `trackNumber` / `discNumber` on `Song`; Android's legacy TRACK value encodes disc 2 track 7 as 2007, while modern tags may be strings such as `7/12`. `sortedInAlbumOrder()` puts tagged songs in disc-then-track order, resolves duplicate positions by title/id, and leaves untagged files last in deterministic title order. Apply it only when opening or playing an album: the all-songs library still owns its user-selected sort. The manual filesystem scan reads the same tags with `MediaMetadataRetriever` because bypassing MediaStore must not mean discarding the tracklist.

### The video options sheet

**`ui/video/VideoOptionsSheet.kt` is two panes, not one scroll.** Pane 1 is a fixed action list (Play next, Add to queue, Watch later, Save to playlist, Download, Go to channel, Share, and the two muted "stop recommending" rows); pane 2 is the playlist picker, whose entire body is one `LazyColumn` with the search field above and New playlist / Done pinned below. [scar] That split is the whole point of the file: the previous single-column version laid roughly 1100dp of fixed rows into a sheet that gets about 890dp, in a `Column` with no scroll, so the bottom rows were clipped with nothing logged - and because the inner playlist list was capped at 340dp, the overflow was identical at zero playlists and at three hundred. **A bottom sheet whose content does not scroll has a silent hard ceiling, and an inner scroller does not save an outer non-scroller.** Do not fold the picker back into the actions pane, and do not add a section to pane 1 without checking the height; pane 1 scrolls only as a landscape backstop, not as room to grow.

Saving is add-only and multi-target - the picker stays open so a video can go into several playlists, and only the terminal rows (Watch later, the two queue actions) close the sheet behind their check. `alreadyIn` covers **device playlists only**, deliberately: the account's would cost a browse call per row for a checkmark, and saving twice is a no-op on both sides.

**Every surface goes through `VideoOptionsSheetHost`** [scar], which wires the sheet and the download hand-off to a `HomeViewModel`. The player keeps its own call, since it drives `VideoPlayerViewModel` and conditions two actions on the playing video. The host exists because per-call-site wiring is what let the Home feed ship with `onEnqueueVideo` unset - the parameter defaults to null, a null hides the whole queue section, and nothing compile-fails. A new surface is three lines and cannot be half-wired.

## 10. Subscriptions and the blocklist

**Two stores, one button.** **Account subscriptions** are the signed-in account's, read from `FEchannels`, written with `subscription/subscribe`. **Local subscriptions** are device-only (`data/LocalSubscriptionsRepository.kt`, prefs `local_subscriptions`) and never visible to YouTube.

**`data/SubscriptionActions.kt` is the only place that decides what a Subscribe tap means.** Three ViewModels drive that button - video player, Shorts, `ChannelViewModel`. Subscribing writes wherever `ThemePreferences.subscribeTarget` says; on `auto`, the account when signed in and the device otherwise. **Unsubscribing ignores the target and clears both stores**: a toggle that turned off in one place and left the channel followed in the other leaves the button reading "Subscribe" for a channel the user still follows, which is the UI lying. The sign-in wall appears only when the user explicitly chose the account target, which is why `requireSubscribeLogin` exists separately from `requireLogin`. The button binds to `isSubscribedToChannel` (account OR device), never `engagement.isSubscribed`, which only knows about the account.

**The local feed is built from each channel's Atom feed, not InnerTube.** Nobody assembles a device-local feed server side, so `getLocalSubscriptionsFeed` merges one request per followed channel, which makes the per-channel source the whole decision. The feed is ~50 KB against roughly 1 MB for the equivalent browse (10 MB versus 200 MB on a 200-channel refresh), needs no client version, cookies or visitorData, and is the only one of the two carrying a real ISO timestamp - InnerTube only says "3 days ago", and merging fifteen channels on prose that coarse shuffles the top arbitrarily. Hence `VideoItem.publishedAtMs` as the merge key. What RSS lacks is duration and live status, which is the trade the "Fast Subscription Refresh" setting states out loud.

**Fast mode means "RSS, else browse".** [verified August 2026] Some channels answer their own advertised `rssUrl` with a 404 despite plenty of uploads, while others served fine from the same IP seconds later. Treating that as "no uploads" drops the channel silently and, for someone following a handful, empties the tab and reads as a network failure. So `getLocalSubscriptionsFeed` falls back to `channelVideosWithTimestamps` per channel, costing a request only where needed. **Do not optimise that fallback away** - but see §7 for the 429 exception, which is the one refusal it must not answer. Fetches run `FEED_CONCURRENCY` (6) at a time; unbounded would mean hundreds of sockets on a pull-to-refresh, and `UploadCheckWorker` needs the same ceiling for the same reason. **The parser must stay namespace-unaware** (`XmlPullParserFactory` with `isNamespaceAware = false`, *not* `android.util.Xml.newPullParser()`, which turns namespaces on), with prefixes stripped so the Atom `<title>` and Media RSS `<media:title>` collapse onto one local name. The empty-feed message blames the connection only when there genuinely is no network.

**The channel rail is a filter, not navigation.** Ordered by the newest upload each channel has in the current merged feed, with channels absent from that snapshot following alphabetically - derived locally rather than trusting an undocumented order from the subscription-list response. Tapping an avatar selects that creator and loads their Videos tab into the feed below; filtering only the merged snapshot would be wrong because a followed channel can have hundreds of uploads and nothing in it. Feed controls filter by upload age and reverse order without refetching, and offer no local Live or Shorts filter because fast RSS carries neither.

**Import/export** (`data/SubscriptionTransfer.kt`): NewPipe/PipePipe/Tubular `subscriptions.json`, the same family's backup archive (`PipePipeData-*.zip` / `NewPipeData-*.zip`), Takeout `subscriptions.csv`, and OPML - **sniffed by content**, not by extension or MIME type, both of which providers lie about. The backup archive matters because PipePipe's obvious menu entry ("Export Data") produces the zip, so that is what people arrive with. Inside is the app's whole Room database, read directly [verified August 2026]: `subscriptions(uid, service_id, url, name, avatar_url)` plus `feed_group` / `feed_group_subscription_join`. SQLite needs a real path, so `read()` takes a scratch `File`; entry names are never used to build it. Every column but `url` is optional, since the forks differ by schema revision. This is the only import path carrying avatars, so those channels skip the backfill. Non-YouTube `service_id` entries are dropped but counted, so a PipePipe user is told why 40 of their 200 did not come across. Handles and vanity URLs resolve to canonical UC ids through `navigation/resolve_url` (works signed out) and are never stored unresolved, because every other call keys off the UC id. Export writes the NewPipe-compatible shape; Koda's groups ride along under a `groups` key those apps ignore.

The Subscriptions tab (`ui/video/SubscriptionsContent.kt`) has no hard sign-in wall. It blocks only when nothing is followed anywhere, and offers importing as a peer of signing in. Tapping a channel opens the real channel page. `HomeViewModel.logout()` must clear `_accountChannels` explicitly - the tab no longer empties itself on sign-out, so stale account channels would sit there unreachable.

### "Don't recommend"

`data/NotInterestedRepository.kt` holds hidden video ids and blocked channels (prefs `not_interested`), process-wide.

**It is the engine of the feature, not a cache in front of YouTube's.** [verified August 2026] Signed out, InnerTube returns no `feedbackToken` anywhere - not on watch-next, browse or search - because there is no account to record against. It is also the only half that acts immediately; YouTube's own feedback is advisory and takes days.

**Signed in, the dismissal is also sent** (`sendDismissalFeedback` → `youtubei/v1/feedback`), so it cleans up recommendations on youtube.com too. `data/NotInterestedActions.kt` is the one place that decides what a dismissal means: the local hide first and synchronously, the account call fire-and-forget on the caller's scope with its result dropped. It must stay that way - the hide has already happened, nothing waits on the network, nothing rolls back on failure. Tokens ride on `VideoItem.dismissal` because they are single-use and bound to the response that carried them; they are null for RSS, NewPipe and every signed-out item, so propagation is skipped rather than failed.

[verified August 2026] `/next` and `FEwhat_to_watch` lockups carry both "Not interested" and "Don't recommend channel"; `FEsubscriptions` carries only the video hide; **search carries no tokens at all**. The two entries are told apart by `leadingImage`'s `clientResource.imageName` (`NOT_INTERESTED` versus `REMOVE`), **never by the visible label** - that string is localized and differs per surface. YouTube pre-bakes an `undoFeedbackEndpoint.undoToken` into the same response, carried on `UndoableAction.undoToken`. Success is `feedbackResponses[0].isProcessed`, not the HTTP code; like `subscription/subscribe`, this endpoint answers 200 to requests it did not act on.

**Filtering is a derived flow over the raw fetch**, never a write into it. A tap removes the item next frame with no refetch and Undo restores it in place; mutating the fetched list would make undo a refetch that brings the video back somewhere else or not at all. Autoplay-next reads the *filtered* list. Blocking a prolific channel can gut a grid and scroll-triggered load-more cannot fire with nothing to scroll, so a cut below `FEED_TOP_UP_THRESHOLD` requests another page. **Shorts are the exception and filter on ingestion**, because the pager index and `playIndex` both address `_shorts` positionally and a filtered view layered on top would put the pager on item N of one list and playback on item N of another.

Per-surface rules follow the tokens and YouTube's own menus: search offers only the channel block; the Subscriptions feed offers only the video hide (blocking a channel you deliberately follow, from the feed that exists to show it, is a contradiction - unfollow is the tool); the player hides "not interested" for the playing video. Undo is a single app-wide `SnackbarHost` at the root of `MainActivity` - the action comes from five surfaces, two of them overlays above the NavHost, so a per-screen snackbar would be hidden behind the Shorts overlay exactly when needed. That host lives for the whole app, so its `YouTubeRepository` is built lazily (it carries an OkHttp pool and opens EncryptedSharedPreferences). The undo request runs on a `rememberCoroutineScope`, not the snackbar's `LaunchedEffect`, which is cancelled the moment another dismissal replaces it. `NotInterestedScreen` is the permanent list; without it a mis-tap weeks ago is an invisible, unfixable hole in the feed.

## 11. Channel pages (`ui/channel/`)

A creator is a full screen (`ChannelScreen.kt`), not the bottom sheet it replaced.

**The organising fact is that a channel page describes itself, and the code lets it.** The first browse returns the tab list with each tab's own `params`, every sort order with its own continuation token, and every next page as another - all signed out. So `YouTubeRepository` holds exactly one hardcoded channel browse parameter (`CHANNEL_VIDEOS_TAB_PARAMS`, kept only as the fallback for a response whose tab list failed to parse) and **the tab row is built from the response rather than an enum**. That is coverage, not tidiness: tab sets genuinely differ - a musician has "Releases" where a teacher has "Courses" and a large channel has "Podcasts" and "Store" - so a fixed set draws empty tabs on channels lacking them and hides real ones on channels with more, both silently. **Do not reintroduce a hardcoded tab list.**

**Tabs are classified by their `params` prefix, never their title** - the title is localized, so matching the English word falls back to a generic layout for most of the world. `ChannelTabKind.OTHER` is not a failure; it is what makes an unrecognised tab render as a grid of whatever it contains, with no code. `ABOUT` is the one kind the data layer never produces: About is an engagement panel behind a token the header carries (`ChannelHeader.aboutToken`), so it costs a request and only when opened. Community posts (`backstagePostRenderer`) carry a single attachment - image, carousel, shared video or poll.

**One scroller, not a fixed header over a scrolling well.** Header, tab row and content share a single `LazyVerticalGrid` on a six-column base, so a video spans six, a playlist three and a Short two, and the header scrolls away under the tabs. The grid's content padding is the page's only gutter (`CHANNEL_GUTTER`), which is why the banner and tab strip use `bleedHorizontally`: Compose has no negative padding, so the constraint is widened and the child placed back over the gutter it was given.

**`LazyGridScope` carries a `count`-based `items` member, and a member shadows the list-taking extension of the same name.** `items(items = …, span = …)` resolves to the member and fails on argument names rather than falling through, and importing both `foundation.lazy.items` and `foundation.lazy.grid.items` into one file makes that harder to read. `spanItems` / `spanItemsIndexed` in `ChannelTabs.kt` route every grid list through the member once. **This is not channel-specific - it will bite the next `LazyVerticalGrid` in this codebase the same way.**

**Opening a playlist is an in-screen child through `PredictiveBackStack`; opening another channel is a real navigation.** A playlist belongs to the creator on screen, another creator belongs in the back stack, which is why the route deliberately does not use `launchSingleTop`. **Every entry point routes through one `openChannel` lambda in `MainActivity`, and the overlays step aside**: the video drops to its mini bar and keeps playing, which is what someone tapping a channel name mid-video wants; Shorts close outright, having no minimised form. `ChannelViewModel` is scoped to the nav entry, so channel-inside-channel gives the second its own instance and back finds the first as it was left; tabs cache per tab and never refetch on a switch.

**`ChannelHeader.accountSubscribed` is `Boolean?` and null means "the response did not say", not "no".** The browse normally reports it for free; when it does not, `ChannelViewModel` falls back to walking `getSubscribedChannels()`, because showing "Subscribe" for a followed channel is the UI lying. Blocking from the channel page is local-only and honestly so: YouTube's dismissal tokens ride on a feed item, not a channel.

**The channel screen and `ArtistScreen` are two screens sharing one header.** A discography and an upload feed are genuinely different content so they stay separate, but the person is not, so `ui/channel/CreatorHeader.kt` is shared and takes the difference in an `actions` slot - Subscribe and Share on one side, Play/Shuffle/Radio on the other. The artist page makes one channel browse of its own purely for banner, tick and subscriber count; that is its only reason to. The music artist page lives inside the Library tab rather than on a route, so the cross-link goes through `HomeViewModel.pendingArtistPage`, which `HomeScreen` consumes as it routes to the tab and turns the video toggle off.

**`YouTubeLinkParser` handles channel links** - `/channel/UC…`, `/@handle`, legacy `/c/` and `/user/` - and hands back `channelRef` unresolved, because the parser runs on every keystroke in the search field and `resolveChannelId` is a network call. Trailing segments are dropped on purpose: `/@handle/videos` is a link to a channel.

## 12. Settings

All settings live in `data/ThemePreferences.kt` (prefs `ivor_music_theme_prefs`, one `MutableStateFlow` plus KEY constant plus private getter plus public setter each). A new setting threads through **five files**:

1. `ThemePreferences` - StateFlow, KEY, getter/setter.
2. `ui/theme/ThemeViewModel.kt` - the flow plus a `setX()` delegate.
3. `MainActivity.kt` - collect in `setContent`, add a param pair to `MusicApp`, pass through to `SettingsScreen` (threaded twice).
4. `ui/settings/SettingsScreen.kt` - new params, passed to whichever page owns it.
5. `ui/settings/SettingsPages.kt` - the actual row.

**Then add it to `buildSettingsSearchIndex` in `SettingsSearch.kt`.** A setting missing from the index is unfindable and there is no compile error. That is the one omission here that fails silently. **Backups need nothing** - `BackupRepository` copies the whole prefs file key by key.

**Settings is a hub and eleven detail pages, not one scroll.** `SettingsScreen.kt` holds the hub, the page router and every dialog; `SettingsPages.kt` the pages; `SettingsComponents.kt` the shared rows; `SettingsSearch.kt` the index and matcher. Pages are a `SettingsPage` enum driven by `AnimatedContent`, **not** nav routes: `SettingsScreen` takes 106 parameters [drifts] and a destination per category would repeat that list twelve times.

**A page big enough to own a file gets one.** `DISPLAY_SIZE` lives in `ui/settings/DisplaySizeSettings.kt` and `SPONSORBLOCK` in `ui/settings/SponsorBlockSettings.kt`, rather than in `SettingsPages.kt`. `DISPLAY_SIZE` is reached from a row on Appearance rather than the hub, because it is one setting rather than a category; `SPONSORBLOCK` earns a hub row of its own because it is eight categories with three states each. Its back goes to Appearance, not the hub - it is opened from there and the value is usually adjusted more than once. A page that is really one control with a preview is the case for this shape; a page that is a list of rows belongs in `SettingsPages.kt` with the rest. Back unwinds one step at a time - open page, hub, clear the query, leave.

**The updater reports a hand-off, never a download it does not own.** `ui/settings/UpdateScreen.kt` is a `NavHost` route; About is `ExpressiveAboutDialog` inside `SettingsScreen.kt`. Koda holds no `REQUEST_INSTALL_PACKAGES` permission and writes no APK: the download button fires `ACTION_VIEW` on the GitHub asset URL and the browser plus the platform installer do the rest. That is the security posture, not an unfinished feature, so an in-app downloader or installer is a different decision with a different threat model rather than a natural next step. What the screen owes the user is the truth about the tap - `openExternal` returns whether an activity took the intent, a started download is acknowledged by file name, and a device with no handler says so instead of leaving a button that appears broken.

**Local Only is a state of the update screen, not a replacement for it.** [scar] The route used to swap in a full-screen `LocalOnlyNotice`, which hid the installed version, build, build type, Android version and ABI - every one of them already on the device and needing no connection - behind a page with no visible back control. `UpdateScreen` takes `localOnlyMode` and renders `UpdateResult.LocalOnly` where the network result would sit, keeping the top bar and the installed-build card. The preference is a `LaunchedEffect` key rather than an early return, so turning it off starts the check that was refused and turning it on stops offering a release that cannot be fetched. The repository never returns `LocalOnly` - it holds no Context - which is why the decision belongs to the screen. `LocalOnlyNotice` remains correct for the video tabs, where there is genuinely nothing local to show.

Rows to copy, all in `SettingsComponents.kt`: `SettingsRow`, `SettingsToggleRow` (whole row is the hit target), `SettingsHubRow` (category plus live value), `SettingsCard`, `SettingsSection`, `SettingsDivider`, `SettingsDetailScaffold`. They read colors from the theme - do not add `textColor`/`accentColor` parameters back. Destructive rows take `SettingsRowDefaults.destructiveTint`. **Every hub row shows the live value of what is inside it** ("Dark, Vibrant", "412 MB cached"); a category row without one is a worse version of the flat list this replaced. Dialogs stay hosted by `SettingsScreen` and are opened by pages through callbacks, because a dialog owned by a page dies with the page transition. `AlertDialog` with `containerColor = surfaceContainerHigh`, `RoundedCornerShape(32.dp)`, 64dp rounded icon box, spring `scaleIn` via `AnimatedVisibility`.

Theming beyond light/dark: `color_palette` (default `dynamic`) chooses between wallpaper-based dynamic color and the fixed palettes in `ui/theme/ColorPalettes.kt`, applied in `ui/theme/Theme.kt`.

**Defaults worth knowing.** The player style defaults to `EDITORIAL`, and the device music library (`load_local_songs`) defaults to **off** - the audio permission request is triggered by that setting being on, so a default of on met anyone skipping onboarding with a system dialog for a feature they never asked for. `migrateLoadLocalSongsDefault()` keeps existing installs on the old `true`: the Settings toggle is the only writer of that key, so an upgrading user who never opened that screen has nothing stored and would otherwise find their library emptied. It needs its own one-shot marker rather than a lazy check, because `onboarding_completed` flips to true for fresh users too.

## 13. Identity: auth, profiles, backup

### Authentication

- Login is a WebView (`YouTubeAuthDialog`) and cookies are captured from the **`music.youtube.com` cookie jar specifically**, never the current page URL [scar] - mid-login pages sit on `accounts.google.com`, whose jar also has a SAPISID, and saving that produces a "logged in but anonymous" state.
- `SessionManager` stores the cookie string in `EncryptedSharedPreferences`; `isLoggedIn()` means cookies exist.
- Authenticated calls sign with `YouTubeAuthUtils.getAuthorizationHeader()` (SAPISIDHASH, **per-origin**) plus `Cookie`, `Origin`, `X-Goog-AuthUser: 0`. `postWatchApi()` is the canonical helper for www.youtube.com.
- Write actions require login, and `subscription/subscribe` returns 200 even signed out, so always guard with `isLoggedIn()`.

### Profiles

An identity is a `Profile` (`data/ProfileManager.kt`): a **YouTube profile** with a stored cookie string, or a **local profile** with no Google account. "Signed out" is not a special case - it is the local profile that always exists, which is why the roster is never empty and the avatar opens the switcher either way.

**Switching is one preference write, and that is the whole trick.** Every consumer resolves the session fresh per call: `SessionManager.getCookies()` is a preference read, and NewPipe's downloader, though `NewPipe.init`'d once, holds a `SessionManager` that resolves the same way. Redirecting the active profile moves the entire app onto another account without touching any of the 27 login-state call sites [drifts]. **`SessionManager` therefore kept its public API byte-for-byte - do not "clean it up" into something profile-aware.** A switch needs no re-authentication, costs no network, and works offline.

**The hard half is invalidation** (`data/AccountSwitcher.kt`, the one place that decides what a switch means). `visitorData` is the one that matters: it is the anti-bot identity, cached in the repository companion, persisted device-wide, and prefetched independently by `MusicService.onCreate` and `VideoPlayerViewModel.init`. Replaying one account's token under another is exactly the flagged-token case, so it is dropped from memory *and* disk and left to re-mint. The caption cache is deliberately **not** cleared - it is keyed by video id, and a video's subtitles are the same whoever is watching.

**Nothing can be reached directly, because there is no DI.** Everything account-derived observes process-wide `ProfileManager.activeProfileId` and resets itself: `HomeViewModel`, `VideoPlayerViewModel`, `ShortsPlayerViewModel`, and `MusicService` - a second process-level holder with its own repository, its own visitorData prefetch, and a five-minute cache of the account's recommendations and playlists served to the media browser, which without this would list one account's playlists while the app is signed into another. All `drop(1)`, since the flow replays the current value on subscribe and that is not a switch.

**Scope of data is a deliberate split.** Local subscriptions, the blocklist and **watch history** are keyed per profile (`profileScopedKey`), because all three shape recommendations and belong to the identity whose feed they shape. Playlists, liked songs, downloads, stats and theme stay device-wide. [scar] History was on the device-wide side until it was noticed that every profile saw every other profile's watches - and since the taste-based video feed is built from that list, one account's recommendations were being shaped by another account's viewing. Its stored key is per-profile while its flow is process-wide, so `AccountSwitcher` must reload it on a switch, exactly as it does for the other two. The profile migrated from a pre-profiles install inherits the **un-suffixed** keys, so upgrading does not orphan anything.

**`Profile.datasyncId`** is YouTube's own account id (`responseContext.mainAppWebResponseContext.datasyncId`, present on every authenticated response [verified August 2026 across `account_menu`, `FEsubscriptions`, `FEwhat_to_watch`, identical in all three]). [scar] Nothing wrote it until the backup work, so `addYouTubeProfile`'s dedupe had never once fired and signing back into an account already in the roster silently added a duplicate row. It is **null until the first authenticated call lands**, so anything matching on it needs a null path.

**A YouTube profile with no stored cookies is a different state from an expired one, and the switcher says so.** `expired` means YouTube rejected a session that still exists and can be refreshed; no session at all means it has never been signed into here, which is what every backup-restored profile is. [scar] **Both taps must actually reach the sign-in flow** - the row promised a reconnect while `onClick` only switched profiles, so tapping the already-active profile did nothing. Reconnecting goes through `onReconnectProfile` with `addAsNewProfile = false`, never the add path: adding captures the session into a *new* profile, stranding the existing one's subscriptions and blocklist on an id nothing is active on.

Two more: **adding an account must clear the WebView cookie jar first** (Google's login page auto-continues as whoever the jar holds, so otherwise a second account silently hands back the first; stored sessions are untouched by the wipe), and **signing out of the last profile disconnects the account in place rather than deleting the row**, keeping the id so device-local subscriptions and blocklist survive - they never needed an account. Playback deliberately continues across a switch; streams are already resolved, and killing someone's music because they checked another account is a bad trade.

### Incognito

`data/IncognitoMode.kt`, toggled from the account sheet, off by default.

**Gated at each write, never at the call sites.** `VideoHistoryRepository.addVideo`, `SearchHistoryRepository.addQuery`, `StatsRepository.addPlayEvent` and both of `YouTubeRepository`'s playback reporters check it themselves, so a sixth surface that records something inherits the behaviour instead of having to remember. That is the whole reason it is process-wide state rather than a flag on a ViewModel.

**It suppresses recording, not doing.** Playback, downloads, playlists, likes and subscriptions are untouched, and the row's subtitle says so. [judgement] Someone reading "incognito" as "nothing I do is saved" would be surprised by a download appearing later, and silently discarding a save the user asked for by name is a different feature wearing this one's label.

**Persisted rather than held in memory, so it fails closed.** A service restarted after the app was evicted must not start recording again on its own. The preference is written before the in-memory flag for the same reason - the reverse order records nothing this session and everything after the next process death. It is excluded from backups because it describes a session.

**The indicator is not optional.** A chip beside the avatar whenever it is on, because a mode that silently stops recording is a promise, and a promise whose state cannot be seen is one someone will assume is off at the wrong moment.

### Backup and restore

One versioned zip holding the whole install (`data/BackupTransfer.kt`, `BackupRepository.kt`, `ui/settings/BackupScreen.kt`). Not interoperable and not trying to be - `SubscriptionTransfer` is the interoperable one.

**A backup copies the stores, it does not serialize the models.** `BackupRepository` holds three allowlists - preference *files*, `filesDir` directories, `filesDir` files - and a preference file is copied key by key, so every setting added from now on lands in backups free. The cost, stated where it is paid: **the allowlists restate names that are private constants in the stores that own them, and no compiler checks that.** Rename a preference file or stored file and it silently drops out of every backup taken afterwards.

**The exclusions are deliberate.** Session cookies (a credential, and the file is meant to be safe in Drive), `visitorData` (carrying one device's onto another is the flagged-token case), the download-migration flag (a restored `true` permanently skips a migration that never ran), the last-played snapshot and both playback-session files, and the incognito flag (they describe a session, not a preference - a restored incognito would silently stop a second device recording history for a reason its owner never chose), and downloads - the media is far too large and its metadata without the media is a library of broken rows.

**The profile split is carried structurally**, because raw keys would not survive the trip: `profileScopedKey` suffixes with a device-local UUID except for the legacy-migrated profile, so a raw `subscriptions` key restored elsewhere lands on whichever profile happens to be that device's legacy one. Local subscriptions, the blocklist **and watch history** are keyed by *backup* profile id in the file, and the restore recomputes the real key with the receiving device's legacy id after resolving each backup profile to a local one - by id first, then by `datasyncId`. History moved onto this path the day it became profile-scoped, and the `video_history` entry came out of `PREFERENCE_FILES` in the same change: a profile-scoped store left in the raw copy is the failure that paragraph describes, and nothing compile-fails when one is. The watch-history count in the manifest sums the per-profile entries for the same reason - read out of the raw preference map it would silently report zero. `ProfileManager.restoreProfiles` is the only place a profile is created with an id rather than a fresh UUID, and it has to be: a restored profile with a new id is an identity with none of its own data.

**Restore replaces the allowlists, merges the roster, and restarts the process.** Merging is the one exception, because a profile already here holds cookies the file does not, and signing someone out of an account they are using is not something a restore should do; restored YouTube profiles come back `expired = true`, which already means "this is the account, sign in again". The restart exists because with no DI a restore cannot reach what it just invalidated - per-instance `ThemePreferences` flows, the process-wide companion caches, `MusicService`'s own repository, and SharedPreferences' in-memory map. **Every write on the restore path is `commit()`, never `apply()`**, since the process is killed deliberately and a queued write dies with it; hence the `commitNow` parameter rather than switching wholesale. `BackupTransfer` is format only and touches no Context, so its edge cases can be reasoned about without a device. Zip rather than one JSON document because playlist covers are binary and a chosen one is an irreplaceable photo, and because a full play history compresses hard. Entry sizes are bounded and entry names are never used to build a path.

## 14. Player styles and queues (`ui/player/`, 8 styles)

**Naming trap: the `POSTER` enum key is the "Canvas" player.** The old kinetic-type Poster style was rewritten in place as full-bleed album art; the constant and file name (`PosterPlayerContent.kt`) kept the old key for prefs compatibility while every user-facing string says "Canvas". Searching "Canvas" will not find the enum; searching "Poster" lands on a file that does nothing poster-like. **Do not "fix" this** - the stored value is the string `"POSTER"` and renaming resets every user's style.

Adding or renaming a style touches **four** places (an omission compiles but misbehaves): the `PlayerStyle` constant in `ThemePreferences.kt`; a `<Name>PlayerSheetContent(viewModel, ...)` composable in `ui/player/<Name>PlayerContent.kt`; a branch in `ExpandablePlayer.kt`'s `when (playerStyle)`, the only dispatch point; and `playerStyleCatalog` in `PlayerStyleCatalog.kt` (label, subtitle, icon, and the `MaterialShapes` polygon that is the style's die-cut identity in the wheel). **The catalog is the only list** - settings picker, onboarding and `rememberPlayerStyleWheelEntries()` all derive from it. That used to be three hardcoded lists and the way one went stale. A new style also wants a branch in `PlayerStylePicker`'s `PlayerStylePreview`; that `when` is exhaustive, so a missing one is a compile error rather than a silent gap.

**Swipe-to-skip is one contract in `SwipeToSkip.kt`, not a per-style gesture.** `rememberSwipeToSkip(onNext, onPrevious)` plus `Modifier.swipeToSkip(state)` and `swipeToSkipFollow(state, factor)`; one state is shared by a style's artwork and its title/artist block, so both commit at the same 90dp threshold with the same spring home, and a drag crossing between them cannot skip twice (Compose keeps the gesture with the node that took the down). [scar] It exists because the gesture had been copied by hand into each style and **three of the eight - Classic, Bento, Dial - silently never got one**, while Morph drifted to its own threshold. Two styles keep their own reaction on purpose: **Sticker's peel** throws the art off and slaps the next on (its identity, not a spring-back), and **Gesture's swipe steps the queue** through `onSongChange` because its carousel follows `currentIndex` and would fight a ViewModel skip. **The mini player is deliberately excluded** - horizontal there is dismiss, and one small bar cannot mean both.

**Both pickers show every style.** Onboarding used to offer a curated pair; that was changed deliberately, because people pick a look at first run and were not finding the rest. `PlayerStylePicker` is non-lazy for exactly this reason: it renders inside onboarding's `verticalScroll` column and inside the settings page's `LazyColumn` item, and a lazy grid nested in a scrollable parent has unbounded height.

**Eight styles, three queue views**, and that is the ratio to keep. `ExpressiveQueueView` (Classic), `GestureQueueView` (Gesture) and `EditorialQueueView` (the other six) draw genuinely different rows, so the *behaviour* is shared and the visuals are not. `ui/components/QueueReorder.kt` holds the drag state machine and `QueueRowContainer.kt` the lift, swipe-to-remove, undo snackbar and `QueueDragHandle`. **Both live in `ui/components/` rather than `ui/player/` because video mode's `VideoQueueSheet` uses them too**, which is why `queueRowKeys` takes ids rather than `Song`s. A fourth queue view uses them rather than growing a fourth implementation - that is exactly how reordering ended up in one view of three and removal in two.

**Opening any music queue focuses the current song once.** `rememberFocusedQueueListState` waits until the lazy list is laid out, smoothly brings the current row into view and centers it where the list bounds permit; the two queue designs with a now-playing header pass one leading item. It deliberately does not follow later track changes or restart after an interrupted animation, because once the listener scrolls or reorders, the list belongs to them. Closing and reopening the queue creates a fresh state and focuses again.

Four rules those files enforce, each something that was wrong before:

- **The visible drag handle is the primary path; long press is only the accelerator.** A queue row is tappable, so `Surface(onClick)`'s clickable sits deeper in the modifier chain than a long-press detector on the same row and wins the gesture; and moving before the timeout hands the pointer to the list's scroll. `LibraryScreen`'s playlist reorder splits the same two ways and only gets away with a row long-press because its clickable is *disabled* in manage mode - a queue cannot do that, since tapping a row must skip to that track.
- **The swap is resolved once per frame from a `withFrameNanos` loop, never in the pointer callback.** `layoutInfo` refreshes only after relayout and several pointer events arrive per frame, so a per-event swap measures against a stale snapshot and the row walks away from the finger.
- **Queue row keys are occurrence-qualified, never index-qualified.** A queue can hold the same track twice so a bare id crashes on duplicate keys, but `"$id_$index"` re-keys every row a moved row passed and `animateItem` then has nothing to animate.
- **Auto-scroll only when the list can consume it.** A `scrollBy` the list cannot take is passed on through nested scroll, and the video queue lives in a `ModalBottomSheet` - unguarded, dragging a row against the top drags the sheet closed mid-reorder.

Music writes the session once on release (`moveQueueItem(..., persist = false)` per crossing, then `commitQueueOrder()`); per-crossing writes turned the gesture into stutter.

**Video mode's queue is edited through `VideoQueue` itself, not the ViewModel.** `moved`, `removedAt`, `withInserted` live on the data class because `index` points at the playing video and every edit must keep it there - a reorder crossing the current index shifts it, a removal above it decrements it - and there is no id to fall back on. Two removals are refused outright, with no control offered rather than one that fails: the last remaining entry, and **the entry that is playing**, because video mode has no playback service to hand off to and the player would go on playing a video the queue no longer contains. `enqueueVideo` starts an ad-hoc queue (`VideoQueue.adHoc`, `playlistId` null) from whatever is already playing, which is what makes "add to queue" work from a feed or search. `moveQueueItem` and `removeQueueItem` check `timelineAgreesAt` before touching the player, as `skipToQueueItem` always has: the UI queue and the ExoPlayer timeline can drift, and editing the wrong index is worse than editing none.

**`addToQueue` had no caller for a long time** except the auto-queue, so adding one track to what was playing was impossible. `ui/player/SongOptionsSheet.kt` is the entry point now - Play next, Add to queue, Add to playlist, Like, Download - opened by a long press through `Modifier.songRowClick` and hosted **once** in `HomeScreen` (`songOptionsTarget`), because it acts on the `PlayerViewModel` that lives at that level. Screens take `onSongLongPress: ((Song) -> Unit)?` and pass it down rather than hosting their own.

## 15. Home screen widgets (`widget/`, six providers)

Now playing, Quick controls, Stack, Up next, Canvas and Disc - all Glance, sharing one design kit (`PlayerWidgetUi.kt`) and one state layer (`PlayerWidgetCommon.kt`). Three rules hold them up and every one is a bug that shipped once.

**A `MediaController` may only be touched on its application thread, and Glance never gives you that thread.** `provideGlance` and every `ActionCallback.onAction` run on a background dispatcher while the controller binds to the main looper, so a direct `controller.play()` throws `IllegalStateException` - into a `catch (e: Exception)` that logs and moves on, which is why the symptom was "the buttons do nothing, sometimes". Everything that speaks to a session goes through `withController`, which wraps the block in `withContext(Dispatchers.Main)`.

**Widgets render from a stored snapshot, never a live session read.** `MusicService.onEvents` writes `player.toWidgetSnapshot()` into `PlayerWidgetStore` on its own player thread, inside the callback that reported the change, then pushes; a redraw is a preference read. The version that bound a controller per render was wrong constantly for three compounding reasons - the read happened at an arbitrary moment relative to the change that triggered it, six widgets raced for the same answer, and a bind that timed out blanked every widget to "Tap to listen". A controller is bound for exactly two things: issuing a command, and bootstrapping the store the first time. **`onEvents` rather than individual overrides is deliberate** - the scattered version pushed only on the *pause* edge of `onIsPlayingChanged` and had no push at all for shuffle or repeat.

**Play/pause masks locally; skips do not.** Media3 applies `play()`/`pause()` optimistically, so the state reads straight back through the same controller. Skips cannot, because `onPlayerCommandRequest` intercepts `COMMAND_SEEK_TO_NEXT`/`PREVIOUS` to route them through the crossfade engine and answers `RESULT_ERROR_NOT_SUPPORTED`, which suppresses the masking - a read taken immediately after a skip returns the *previous* track. Skips therefore settle before reading back. Relatedly the snapshot's `isPlaying` is `playWhenReady`, not `Player.isPlaying`: the widget shows intent, so the glyph flips on tap rather than after the first buffer.

Design constraints: **shape carries the hierarchy** (no ripples, no morph, no springs in a RemoteViews tree), so the hero play button is the only fully round control and everything else a 16dp squircle - one hero per widget. **Every control gets a container**; bare glyphs on a tonal card read as print, not buttons. Corner radii come from tinted shape drawables because `GlanceModifier.cornerRadius` is a no-op below API 31 and minSdk is 30. Colors come from `KodaWidgetTheme`, resolving the same palette/AMOLED/dynamic preferences the app does through the shared `kodaColorScheme` - Glance's default is raw system dynamic color, which makes the widgets look like another app's. The only literal color is the scrim over artwork. **A widget clips silently when content overruns the cell**, so a layout that grows is measured against the size bucket rather than eyeballed (`StackPlayerWidget.belowCoverHeight` is the pattern: add up everything under the cover and give the cover the remainder). With `SizeMode.Responsive`, `LocalSize.current` reports the matched *bucket*, not the real cell.

## 16. UI conventions

- **Every video frame big enough to notice goes through `ui/components/VideoThumbnail.kt`.** [scar] `VideoItem.highResThumbnailUrl` rewrites a feed's mq/hq/sd URL to `maxresdefault`, which YouTube only generates for sources uploaded at 720p or better - so it 404s for a large minority of videos, and a card that requested only that one drew an empty plate with nothing logged. The feed's own URL is drawn underneath and the high-res fades in on top, the layering `SongArtwork` already used for covers. Coil never retries a failed request either, so one dropped fetch left a card blank for as long as it stayed in the list; two delayed attempts cover a moment of no signal, and a genuine 404 exhausts them in about two seconds and settles on a broken-image state rather than a spinner that will never finish. The M3 `LoadingIndicator` is held off 180ms so a memory-cache hit never flashes one on a fling. It is also the one place that knows a `device:` id has no URL at all and must draw through `LocalVideoThumbnail`.
- **Material 3 Expressive first** (`LoadingIndicator` with shapes, `FloatingToolbar`, `MaterialShapes`, spring physics), standard M3 second. Do not hand-roll components or animation systems that M3 or `androidx.compose.animation` already provide.
- Compiler-level opt-ins for `ExperimentalMaterial3ExpressiveApi` and `ExperimentalMaterial3Api` are global (`freeCompilerArgs`).
- Shared look: `Surface` cards with `RoundedCornerShape(16.dp)`, `surfaceContainer` colors, `ExpressivePullToRefresh`, staggered `AnimatedVisibility` entrances. Match neighbouring code.
- **Springs for anything touch-driven** (~120 uses [drifts]; `DampingRatioMediumBouncy` is the house default). Reserve `tween()` for crossfades and time-tracking progress.
- **The interface scale is a density override, and that is the only way it could have been.** `IvorMusicTheme` provides a `LocalDensity` whose `density` is multiplied by the user's `ui_scale` (`ScaledDensity` in `ui/theme/Theme.kt`), so all 3,452 `dp` literals across 89 files [drifts] resize at once and every proportion the design was drawn at survives. Retuning the literals would have been the same feature and a permanent tax on every layout written afterwards. Three consequences worth knowing: **`fontScale` is deliberately left alone** rather than divided back out, so `sp` rides along with the chrome and the user's system font setting still multiplies on top; **every `LocalDensity` read in the app is a consumer, never a provider** - the ~30 existing `dp.toPx()` call sites follow the scale for free, and a second provider below the theme would silently desync a subtree from the rest of the app; and **Glance widgets, the media notification and Android Auto do not inherit it**, correctly, since another process draws them and they should match its density.
- **A scale committed mid-drag fights the finger holding it.** `DisplaySizeSettingsPage` previews on every step and writes only on `onValueChangeFinished`, because applying each intermediate value rescales the page the slider is sitting on and moves the thumb away from the touch. The preview is a nested override of the same local, multiplied by `pending / committed` because the page is already drawn at the committed scale.
- Material icons extended is available (`Icons.Rounded.*`).
- See invariants for the color rule and §5 for the design-language policy.

## 17. CI and the release announcement (`.github/workflows/`)

Three workflows, and **every one hangs off an `authorize` job that runs first**: `build.yml` (debug and release APKs, ABI splits, uploaded as artifacts), `codeql.yml` (`actions` and `java-kotlin`, manual build mode running `assembleDebug` because autobuild guesses wrong on Android projects), and `telegram-notify.yml` (star milestones and release announcements). Workflow-level `permissions: {}` is the default in all three; each job re-adds only what it needs.

**Judge APK size from the minified release, never the debug APK.** [verified August 2026] The 4.7 arm64 release was 14.01 MiB versus 11.20 MiB for 4.6; the actual artifact diff put the growth in DEX plus the production Cast, Glance/WorkManager and 25-language resources, not tests or debug tooling. The unminified debug APK was about 104 MiB because it contains full Compose tooling and extended icons, while `testImplementation`, `androidTestImplementation` and `debugImplementation` were absent from the release archive. `androidResources.localeFilters` must stay identical to `res/xml/locales_config.xml`: without it, transitive libraries advertised more than eighty language configurations that Koda does not support and inflated `resources.arsc`. Keep NewPipe's R8 rules narrow to its reflected time-ago patterns and protobuf fields; keeping the whole extractor pins unused services and methods. Rhino's broad keep is different and load-bearing because it executes YouTube JavaScript dynamically. Do not restore the obsolete yt-dlp/Python keep rules unless that dependency itself returns.

**The authorize gate is not a formality and its denials are not bugs to fix.** A run proceeds only when the actor has write access: a same-repo PR is authorized by construction, pushes and `workflow_dispatch` need the actor to be the owner or in `TRUSTED_ACTORS`, and a fork PR needs `author_association` of `OWNER`, `MEMBER` or `COLLABORATOR`. A fork PR from an outside contributor builds nothing, deliberately, because analysing it means running that fork's Gradle build on a runner. Those runs appear as `action_required` and even once approved the gate skips every build job and writes a "Build skipped" summary. Widening the `case` lists is the owner's call per contributor, not a cleanup.

**A red run with no logs is GitHub, not the code.** `The job was not acquired by Runner of type hosted even after multiple attempts`, with an empty `runner_name` and nothing from `gh run view --log-failed`, means no runner ever picked it up. Re-run rather than debug.

**`telegram-notify.yml` does not trigger on push.** It fires on `watch` (stars) and `release: published` only, so a change cannot be verified by pushing and the first live run of any edit is a real release. Test it by extracting the `run:` block and executing it with `curl` and `jq` stubbed, as the current one was checked against a real release payload.

**The APK post is a separate, authorized PR-only path inside `build.yml`.** The release job still cannot run until `authorize` allows it, and fork PRs still cannot enter it because they receive no signing or bot secrets. After the signed universal APK reaches `@ivorisnoob_chat` (or its over-limit artifact link does), the same step sends the accumulated `Changelog:` sections from every commit after the head of the last successful same-branch PR workflow. It reads that checkpoint from Actions history with `actions: read`; canceled and failed runs therefore do not advance it, so their entries roll into the next delivered APK without a writable state file. On the first delivery, an unavailable history response, or rewritten ancestry, it falls back to every commit on the current PR - a possible repeat is safer than a silent omission. The PR title is deliberately absent. Changelogs are plain text, chronological, and split below Telegram's UTF-16 message ceiling. [verified August 2026]

**Telegram's HTML mode is a small, strict parser that rejects the whole message on one malformed tag.** It understands `b/i/u/s/a/code/pre/blockquote/tg-spoiler` and nothing else, capped at 4096 UTF-16 units. Release notes are free-text Markdown, so `notes_to_html` escapes `&`, `<` and `>` first and only then adds tags we control, and **every conversion rule is line-local on purpose** - that is what makes trimming whole lines to fit the budget tag-balanced. The notes budget is whatever the header, asset list and footer leave over, not a constant. If Telegram rejects the markup anyway the message is resent as plain text, because a release with no announcement is worse than one announced unformatted.

**Free text reaches the script as data, never through `${{ }}` interpolation into the shell.** Release bodies and names arrive as environment variables, while APK changelog subjects and bullets are read from Git after checkout. `github.event.release.assets` arrives as `toJSON(...)` and can legitimately be empty, since a release is often published before its APKs finish uploading.

**`OWNER_URL` is the author-link convention and both files share it.** `author_html()` renders the repository owner's login as a link to `https://ivorisnoob.lol` and anyone else as plain text, matched case-insensitively against `github.repository_owner`. Keep the two copies in agreement and never link a non-owner to that site.

## 18. Docs and how work is tracked

**Finishing a piece of work means updating `ROADMAP.md` in the same change.** A planned item that ships loses its section from Planned work and gains a line in Shipped; a fixed defect leaves Known defects, keeping whatever about the diagnosis is worth carrying to the next problem of its kind. **Then correct the prose elsewhere that leaned on the old behaviour** - those paragraphs are what the next decision gets made from, and a stale one will be believed. [scar] Channel search shipped saying account subscriptions carry no `@handle`; they always did, and that paragraph would have talked the next person out of supporting them. This is part of the same commit as the code, not a follow-up and not something to ask about first.

**Keeping this file true is part of the same rule.** If a change contradicts something here, fix the sentence in the same commit. When you add a fact, mark it: `[verified <month>]` for something probed, `[scar]` for something that broke, `[judgement]` for a call someone could reasonably make differently. Re-derive any count or line reference you touch rather than trusting it, and prefer deleting a stale paragraph to leaving it standing.

`ROADMAP.md` is the prose and reasoning; **GitHub issues are the task list.** Most issues quote the roadmap entry they came from, epics carry the `epic` label, and children open with "Sub-issue of #N". A roadmap entry naming a file and line has usually already become an issue, so search before writing a new one. Every open issue carries one label from each of the first three families:

- **`area:`** `interface` / `playback` / `foundations` / `reach`, matching the `ROADMAP.md` headings.
- **`size:`** `XS` / `S` / `M` / `L` / `XL`. **Effort, not importance.** XS is an hour or two in one file with no design decision; S half a day across one or two files with the approach settled; M a few days, several files, or one new screen over existing data; L a week or more, a new subsystem or data model, or a UI-wide sweep; XL multi-week, a new module, app or playback pipeline. Epics carry the size of the whole thing, so an XL parent over M children is expected.
- **`priority:`** `P0` / `P1` / `P2` / `P3`. **Ranked by user-facing impact, deliberately not by what unblocks the most other work.** P0 is wrong today and hit constantly; P1 a noticeable gap in a daily core loop; P2 a real improvement nothing is blocked on, and most of the list; P3 a new surface or platform, or something deferred on purpose.
- Plus ordinary `bug` / `enhancement` / `question` / `documentation`, and `good first issue`, `blocked`, `epic`.

Sizes and priorities are judgements rather than measurements; argue with one and change the label rather than treating it as fixed.

Written for users and contributors, so it carries counts that go stale [drifts]: if you change the palette list, player styles, or the animation/shape mix, re-derive its numbers.
