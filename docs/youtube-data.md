# YouTube data layer (`data/YouTubeRepository.kt`)

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

Two extraction mechanisms side by side: **NewPipe Extractor** for video/artist/playlist search, stream URLs and extraction fallbacks (initialised once with `NewPipeDownloaderImpl`, which injects session cookies), and **raw InnerTube JSON over OkHttp** for music song/release search and playlist browsing, personalised feeds, watch history, engagement, account info. Parsing is manual `org.json` traversal with recursive helpers (`findObjectsByKey`, `findContinuationTokens`, `getRunText()`). No kotlinx-serialization for InnerTube responses.

**Music metadata is identified by links, never subtitle positions** (`data/MusicMetadata.kt`). [scar] [verified September 2026] The live search and `/next` rows for Billie Eilish and Khalid's "lovely" put Khalid at run 2, where the old parser expected the album; playlist rows put the actual album in a separate flex column. `MUSIC_PAGE_TYPE_ARTIST` and `MUSIC_PAGE_TYPE_ALBUM` establish the relationship, with UC/MPRE prefix fallbacks only when page type is absent. Unlinked counts, durations and collaborators must never become albums. Music search and its continuations now use WEB_REMIX before NewPipe, whose `StreamInfoItem` discards album links. Music playlist browse is likewise first for both session states; a fallback must never put the playlist title in `Song.album`.

**Release type and year are data, not an uploader name.** [verified September 2026] Artist cards supply a year, and the Singles & EPs cards distinguish `Single` from `EP`; album headers supply type/year even when individual track rows omit artist and album. `Song.albumId` is the canonical relationship, and `releaseType`/`releaseYear` survive serialized queues/likes and the explicit download, last-song and saved-release stores. The artist's Releases shelf follows each release shelf's More endpoint and continuations, deduplicates by browse id, and sorts descending by year with stable source order for ties and unknown years last. Never infer type from track count, use `dateAdded` as release date, or invent month/day from an upload date: the probed release responses supply only a year. Same-titled editions must open by id, not a title lookup. Sanitized public renderer fixtures and absence/multi-artist/order regression tests live in `MusicMetadataTest`.

## The probe-first workflow (follow exactly)

Never write or modify an InnerTube parser from memory or training data. Shapes drift and renderers get renamed wholesale (`commentRenderer` → `commentEntityPayload`, `videoRenderer` → `lockupViewModel`).

1. **Probe the live endpoint before touching Kotlin.** A gitignored `.probe/` helper exists: `py .probe/probe.py <endpoint> '<json body>'` (add `--music` for music.youtube.com). It reads the pinned client version live out of `YouTubeRepository.kt` and signs with the captured session, writing to `.probe/last_response.json`. **Never commit `.probe/`.** Otherwise write a throwaway script in the scratchpad (`py`, not `python`). Set `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` or emoji in responses crash the Windows console.
2. **For logged-in endpoints**, the session comes from the emulator's WebView jar (`adb exec-out run-as <pkg> cat app_webview/Default/Cookies`), sent as a `Cookie:` header and signed with `Authorization: SAPISIDHASH {ts}_{sha1("{ts} {SAPISID} {origin}")}` plus `Origin`, `X-Origin`, `X-Goog-AuthUser: 0`. **The hash is per-origin** - `music.youtube.com` and `www.youtube.com` need different ones. **An empty WebView jar does not mean signed out:** a session established through the app's paste-a-cookie path never opens a WebView and lives only in `yt_music_session.xml` (EncryptedSharedPreferences, keystore-bound, unreadable off-device). Check `shared_prefs/` first and fall back to the captured `.probe/Cookies.db`. Confirm a live session by `logged_in: 1` in the response tracking params, never by HTTP 200.
3. **Inspect shapes with a recursive key search, not by eyeballing.** Save the response, walk it with a `find_all(node, key)` helper, count candidate renderer keys, print one exemplar's key list and the exact paths to title/thumbnail/id. Only then write the parser.
4. **Write parsers the way the file already does:** `optJSONObject`/`optString` chains, `findObjectsByKey` for deep collection, `getRunText()` for text (handles `simpleText` and `runs`), `?.takeIf { it.isNotBlank() }` plus a fallback for every field, try/catch returning empty/null with a log. Note "verified <month year>" in the KDoc so staleness is visible.
5. **Client cheat sheet.** WEB (`webContext()`, `postWatchApi()`) for browse/next/engagement on www.youtube.com; WEB_REMIX (`fetchInternalApi()`) for music.youtube.com; NewPipe's Android-reel/visionOS chain for video VOD playback; ANDROID_VR (fallback IOS) only as the direct stream fallback and caption source.
6. **When an existing call starts failing**, log the HTTP code, the first ~200 chars of body, and `playabilityStatus.reason`. HTTP 400 on browse usually means the pinned client versions are too old - bump them. Empty `streamingData` with status OK usually means stale or missing `visitorData`. Do not loop retries; re-probe and compare shapes.
7. **Be frugal per user action.** One `/next` carries engagement, metadata, related videos and the comments token at once. Parse many features from one response (`getWatchNextData`) rather than adding a request per feature.
8. **Clean up write-probe side effects** (delete test comments) and never commit cookie dumps or response JSONs.

Known browse IDs [verified July 2026]: `FElibrary`, `FEplaylist_aggregation` (playlists as `lockupViewModel`s with `contentType: LOCKUP_CONTENT_TYPE_PLAYLIST`), `VL<playlistId>` (contents; `VLWL` Watch Later, `VLLL` Liked), `FEhistory`, `FEchannels`. Public `FEtrending` is dead (HTTP 400 since mid-2025); video feed order is personalised `FEwhat_to_watch` when logged in, then a taste-based mix from local watch history (`getTasteBasedVideos`), then a generic search cold-start.

## Client and identity

- **Client versions** (`WEB_REMIX_VERSION`, `WEB_VERSION`) are pinned constants that must be bumped periodically; YouTube rejects clients older than a few months. Keep `BROWSER_USER_AGENT` plausible against them - a Chrome version years older than the claimed InnerTube build is self-inconsistent.
- **Stream resolution is NewPipe-first.** Extractor v0.26.3 introduced the Android reel + visionOS workaround for SABR-only responses; Koda pins v0.26.5. The direct `ANDROID_VR` → `IOS` resolver is last-resort only and still supplies captions. Keep `uaForPlaybackUri()`'s NewPipe UA versions in step with an extractor bump.
- **The plain `ANDROID` client is SABR-only and cannot be resolved from.** [verified September 2026] Client 3 at v21.03.36 answers `/player` with `playabilityStatus: OK` and a full `adaptiveFormats`, and **not one entry carries a `url`** - no `signatureCipher` either, just `serverAbrStreamingUrl`. This is not a failure state that logs: a parser reading that response finds formats, finds no URL on any of them, and returns nothing. It is also why NewPipe's Android leg goes to `reel/reel_item_watch` rather than `/player`, and why the winning music stream in practice comes from **VISIONOS** (measured: itag 251 Opus at 160 kbps, which the default "high" quality setting selects). Do not point any resolver at `ANDROID`, and do not read "the response had formats" as "the client works".
- **A missing `visitorData` is now a refusal, not a downgrade.** [verified September 2026] `ANDROID_VR` and `VISIONOS` answer a token-less `/player` with `LOGIN_REQUIRED` / "Sign in to confirm you're not a bot" on most videos (`IOS` still answers OK), where the older behaviour recorded here was OK-with-no-`streamingData`. `getVisitorData()` can still return `""` when a mint fails and there is nothing persisted, so `resolvePlayerStreamingData` mints *before* running the chain rather than spending both clients on a refusal it can already predict. Both signatures still set `visitorDataSuspect`, so the remint-and-retry path is unchanged.
- **A googlevideo 403 on the direct fallback is usually the `visitorData`, not the User-Agent.** [verified August 2026] GVS PO-Token enforcement reached `ANDROID_VR`, and IOS too; it can wall a progressive URL after an initial byte window (measured: first ~1.1 MiB served, then 403 for every byte past it, stable for a given token, roughly half of freshly minted tokens refused). The verdict is keyed on the token, not the video or client - which is why these clients cannot regain primary status merely because their `/player` succeeds. `refreshVisitorDataAfterPlaybackFailure()` is the recovery; a surface that plays direct googlevideo streams without wiring it has no way out of a bad visitor bucket.
- **`visitorData` belongs on every InnerTube call, not just `/player`.** [scar] It is minted, persisted, TTL'd (6h) and re-minted on the bot-check signal - and for a long time browse, next, search and engagement carried none of it, so each was a brand-new anonymous client and a session was hundreds of them from one address. `webContext()` and the browse helpers attach `cachedVisitorDataOrNull()` - a non-suspending read, because these helpers must not block on a mint, and an empty cache sends nothing, which is exactly the old behaviour - plus `X-Goog-Visitor-Id` and the `X-YouTube-Client-Name`/`-Version` headers a real WEB client always sends. **Sending it alongside account cookies is safe** [verified August 2026, live signed-in `FEsubscriptions`: identical `logged_in=1` and near-identical payload with and without].
- Minting is the cheap `youtubei/v1/visitor_id` endpoint, bootstrap-HTML scrape only as fallback, prefetched at both `VideoPlayerViewModel.init` and `MusicService.onCreate`.

## Signed-out behaviour

- **`fetchYouTubeBrowse` used to return an empty string the moment cookies were missing** [scar], so every public read built on it came back empty rather than failing, reading as broken content instead of a missing session - that is what made every video-mode playlist page say "No videos in this playlist" signed out. Public browse ids answer 200 anonymously [verified August 2026: `VL<playlistId>` returns the full item list with no cookies, no auth header, no visitorData], so account headers are conditional and the call is not. The consequence: **an account-scoped browse signed out returns a valid shell rather than an error**, so `FEplaylist_aggregation`, `FEhistory` and friends must gate on `isLoggedIn()` at their own call site.
- **A signed-out playlist browse returns `lockupViewModel`s where a signed-in one returns `playlistVideoRenderer`s** [verified August 2026], which is why `getPlaylistVideos` parses both and why the lockup branch is the normal path rather than the fallback it looks like. **NewPipe's playlist extractor only collects `playlistVideoRenderer`s**, so signed out it returns zero items and throws nothing - reaching for it as the signed-out path was the first fix attempted and produced a silently empty page with nothing in the log. It survives as `getPlaylistVideosAnonymous`, the last resort after the browse parses to nothing, precisely because it reads a different shape. Music playlists walk `browseMusic` and its continuation chain through one helper, `getBrowsePlaylistSongs`, for both session states - `browseMusic` and `fetchContinuation` attach account headers only when there is a session, and a public playlist pages to its end with none. A NewPipe continuation failure is incomplete even when page one returned exactly 100 songs, and must not block the authenticated path. Playlist rows preserve order and duplicates - the same video id can legitimately appear twice.

**A continuation answers in a different container than the page that spawned it, and music never learned the current one.** [scar] [verified August 2026 against a 982-track playlist] Page one puts its tracks in `musicPlaylistShelfRenderer.contents` - 100 rows plus a trailing `continuationItemRenderer` holding the next token. The continuation reply carries neither that shelf nor any `continuationContents.<x>Continuation`, the legacy containers `findRootContents` knew; it answers under `onResponseReceivedActions[0].appendContinuationItemsAction.continuationItems`, again 100 rows plus the next `continuationItemRenderer`. So the token was found correctly and every page after the first parsed to nothing, which capped every playlist at exactly 100 songs *and reported the load complete* - no retry, no fallback, nothing logged. `continuationItemsOrNull` (`data/InnerTubeContinuations.kt`, its own file so a JVM test can reach it) reads that shape, and `extractPlaylistContinuationToken` gained the matching scopes because page two onward has no shelf to scope to. **Its scoping is still load-bearing**: the same page carries a `sectionListRenderer.continuations` token whose reply is a `musicCarouselShelfRenderer` of related playlists, so a bare `findContinuationTokens` over the whole response follows the wrong chain. The video path (`extractVideoPlaylistContinuationToken`) already listed `appendContinuationItemsAction`; only music was left behind, which is why the reports were music-mode only.

## Being throttled

- **Throttling is a state the app holds, not a symptom it re-discovers** (`data/YouTubeRateLimit.kt`). **Only HTTP 429 arms it.** A googlevideo 403 is the PO-Token verdict on `visitorData` and already has a working recovery; routing it here would replace a remint with a five-minute sulk. An InnerTube 403 usually means "you may not read this". The hold gates **discretionary fan-out only** - the subscriptions feed, the avatar backfill, `UploadCheckWorker` - and never playback or anything a user is waiting on. `Retry-After` is honoured, clamped to 30 minutes, and a concurrent 429 can only lengthen an existing hold.
- **The subscriptions feed's "RSS, else browse" fallback must not answer a 429.** [scar] The fallback exists for channels that 404 the feed URL YouTube advertises in their own `channelMetadataRenderer.rssUrl`, and that is the only failure it is right for. A 429 is a verdict on the device: the browse will be refused too, and taking that branch for every channel turns a 10 MB refresh into a 200 MB one aimed at the server that just said stop. `fetchChannelFeedRss` returns `ChannelFeedResult` rather than a list - `NoFeed` and `Failed` escalate exactly as before, `RateLimited` stands the whole refresh down. [verified August 2026: a nonexistent channel id answers 404, so the escalation path is unchanged; feeds are served `public, max-age=900` with no ETag.]
- **The OkHttp disk cache is companion-level because it must be.** OkHttp's `Cache` is a DiskLruCache holding an exclusive lock on its directory, and this app builds a repository per ViewModel - several `Cache` objects on one directory is corruption, not contention. InnerTube calls are POSTs and are never cached, so it can only serve a stale *feed*; an explicit pull-to-refresh passes `forceFresh` and revalidates, because a refresh that visibly changes nothing is worse than the traffic it saves.

## Response shapes

- **Comments** use `commentEntityPayload`: entities in `frameworkUpdates.entityBatchUpdate.mutations`, ordering from `commentThreadRenderer`s in `onResponseReceivedEndpoints`. Legacy `commentRenderer` no longer exists.
- **Feed and related items** are `lockupViewModel`s parsed by `parseLockupViewModel`; `videoRenderer` is legacy but still handled.
- **A collab video names no owner at all.** [verified September 2026, signed out] YouTube's collaborations feature puts up to five channels on one upload, and its `videoOwnerRenderer` then carries **no** `title`, `thumbnail`, `subscriberCountText` or `navigationEndpoint.browseEndpoint` - only an `attributedTitle` ("KSI and 2 more", already localized), an `avatarStack` of every collaborator, and a `navigationEndpoint` that is a `showDialogCommand`. The `subscribeButtonRenderer` carries no `channelId` either. So before `parseCollaborators` the watch page had no channel to open and nothing to subscribe to; the collaborators come free inside that command's `dialogViewModel.customContent.listViewModel.listItems[]` (name, `browseEndpoint.browseId`, `@handle • N subscribers` in `subtitle`, avatar in `leadingAccessory`, `CHECK_CIRCLE_FILLED` in `attachmentRuns` for verified), so listing them costs no request. The dialog is reached structurally, never by matching its "Collaborators" headline, which is localized. **A lockup addresses its channel from the avatar, not from its byline text.** [verified September 2026, signed out, against a live `/next` related list and a channel Videos tab] Every card in that related list came back with an empty `onTap` on the creator text, so reading only `commandRuns`/`runs` left `channelId` null for ordinary videos too and every channel tap paid an extra `/next` through the `video:` fallback to recover an id the response had already sent. It is on the avatar: `lockupMetadataViewModel.image.decoratedAvatarViewModel.rendererContext.commandContext.onTap.innertubeCommand.browseEndpoint` for one creator, and `image.avatarStackViewModel` on the same command slot for a collab, carrying the same collaborators dialog. A channel tab's lockup has no `image` block at all - the page already names the creator - so the `video:` fallback is still the answer there, which is why `getVideoChannelId` ends in the first collaborator: without it a collab card opened a channel page that failed to load. The dialog is read by one host-agnostic helper (`collaboratorsFromDialogHost`) because the nesting between the host and the dialog differs between the two. Subtitle text arrives wrapped in bidi isolates (`BIDI_CONTROL_CHARS`) that must come off before it is split.
- **Chapters** live in the `/next` decorated player bar: `multiMarkersPlayerBarRenderer.markersMap` keyed `DESCRIPTION_CHAPTERS` or `AUTO_CHAPTERS`, each a list of `chapterRenderer { title, timeRangeStartMillis, thumbnail }`; document order is chronological. [verified July 2026]
- **Captions** come from the **ANDROID_VR** `/player` call (IOS fallback), never WEB: `captions.playerCaptionsTracklistRenderer.captionTracks[]`, each with `baseUrl`, `languageCode`, `name`, and `kind == "asr"` / `vssId` starting `a.` for auto-generated. [scar] A WEB `/player` without account cookies answers UNPLAYABLE with no captions block at all, which gave every signed-out user an empty CC menu; the native clients return the full tracklist signed out. `parseCaptionTracks` runs on every `/player` response and `runPlayerClientChain` caches per video id (30 min TTL, LRU 16), so a lazy CC tap normally costs no network. [verified July 2026]
- **Timedtext `baseUrl`s must have their format replaced, not appended.** [scar] ANDROID_VR hands back URLs already carrying `&fmt=srv3` and the endpoint honours the *first* `fmt`, so `"$baseUrl&fmt=vtt"` silently returns srv3 XML under a `text/vtt` MIME type and the subtitle load fails. `CaptionTrack.vttUrl` strips `&fmt=`/`&tlang=` then appends. Do not "simplify" it back.
