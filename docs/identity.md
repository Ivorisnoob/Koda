# Identity: auth, profiles, incognito, backup

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

## Authentication

- Login is a WebView (`YouTubeAuthDialog`) and cookies are captured from the **`music.youtube.com` cookie jar specifically**, never the current page URL [scar] - mid-login pages sit on `accounts.google.com`, whose jar also has a SAPISID, and saving that produces a "logged in but anonymous" state.
- `SessionManager` stores the cookie string in `EncryptedSharedPreferences`; `isLoggedIn()` means cookies exist.
- Authenticated calls sign with `YouTubeAuthUtils.getAuthorizationHeader()` (SAPISIDHASH, **per-origin**) plus `Cookie`, `Origin`, `X-Goog-AuthUser: 0`. `WebApi.postWatchApi()` is the canonical helper for www.youtube.com.
- Write actions require login, and `subscription/subscribe` returns 200 even signed out, so always guard with `isLoggedIn()`.

## A session is a login, not a cookie string

`data/YouTubeSession.kt` - a `profileId`, a `generation` and the cookies as they stood when the request went out.

**Google rotates the session cookies while the app is using them.** The `__Secure-1PSIDTS` / `__Secure-3PSIDTS` pair is re-issued every few hours, and a session that keeps replaying the value captured at login eventually gets answered `logged_in: 0` with an empty subscriptions feed and a blank account name [verified August 2026]. `SessionRefreshInterceptor` folds those back into storage, which is why signing in no longer wears off.

The consequence is the scar: **a rotation is not a new login, so never compare cookie strings to ask "is this still the session I started with"**. [scar] Video history reporting did exactly that - it froze the cookie string when reporting began and required equality on every later ping - so the first rotation mid-video read as a different login and reporting stopped silently for the rest of the video on a perfectly valid account. `generation` is the identity instead: `saveCookiesFor` (a deliberate sign-in) bumps it, `mergeSessionCookies` (a rotation) does not. `SessionManager.currentSession(session)` answers the real question - same profile, still active, same generation - and hands back the *refreshed* cookies to sign with. A held `YouTubeSession.cookies` is a snapshot and goes stale on its own; re-read before each use.

**Every authenticated request is bound to the session it is sent for.** `authenticate()` (`data/youtube/YouTubeHttp.kt`) is the single helper: it sets `Cookie`, the per-origin SAPISIDHASH and `X-Goog-AuthUser`, and tags the request with its `YouTubeSession`. Passing null sends it signed out, which is deliberate for the browse ids that read fine anonymously - an empty `Cookie` header is worse than none. Anything that lands *after* a response - a cookie refresh, the `logged_in` verdict (`noteSessionState`), the account name/avatar/`datasyncId` from `account_menu` - is applied through the tagged session, never to whoever is active now. [scar] All three used to write to the active profile, so switching A -> B with A's calls still in flight mixed A's cookies into B, badged B as expired, or renamed B to A.

**The refresh is a network interceptor, not a `CookieJar`.** [scar] A jar's callbacks cannot say which profile sent the request, and Google rotates the `*PSIDTS` pair on the 302s inside a redirect chain - an application interceptor only ever sees the final hop's headers. Nothing is ever sent from the interceptor; callers assemble their own headers, and a jar handing cookies back would have OkHttp's bridge interceptor replace them.

## Profiles

An identity is a `Profile` (`data/ProfileManager.kt`): a **YouTube profile** with a stored cookie string, or a **local profile** with no Google account. "Signed out" is not a special case - it is the local profile that always exists, which is why the roster is never empty and the avatar opens the switcher either way.

**Switching is one preference write, and that is the whole trick.** Every consumer resolves the session fresh per call: `SessionManager.getCookies()` is a preference read, and NewPipe's downloader, though `NewPipe.init`'d once, holds a `SessionManager` that resolves the same way. Redirecting the active profile moves the entire app onto another account without touching any of the 27 login-state call sites [drifts]. **`SessionManager` therefore kept its public API byte-for-byte - do not "clean it up" into something profile-aware.** A switch needs no re-authentication, costs no network, and works offline.

**The hard half is invalidation** (`data/AccountSwitcher.kt`, the one place that decides what a switch means). `visitorData` is the one that matters: it is the anti-bot identity, cached in the repository companion, persisted device-wide, and prefetched independently by `MusicService.onCreate` and `VideoPlayerViewModel.init`. Replaying one account's token under another is exactly the flagged-token case, so it is dropped from memory *and* disk and left to re-mint. The caption cache is deliberately **not** cleared - it is keyed by video id, and a video's subtitles are the same whoever is watching.

**Nothing can be reached directly, because there is no DI.** Everything account-derived observes process-wide `ProfileManager.activeProfileId` and resets itself: `HomeViewModel`, `PlayerViewModel`, `VideoPlayerViewModel`, `ShortsPlayerViewModel`, `ChannelViewModel`, and `MusicService` - a second process-level holder with its own repository, its own visitorData prefetch, and a five-minute cache of the account's recommendations and playlists served to the media browser, which without this would list one account's playlists while the app is signed into another. All `drop(1)`, since the flow replays the current value on subscribe and that is not a switch. [scar, September 2026] `HomeViewModel`'s reset had left five account lists alone - the video Library's playlists, the notification inbox, Spotlight's signed-in YouTube Music tabs, the selected subscription group and (in `PlayerViewModel`) the add-to-playlist sheet's playlists - so each kept showing the previous account until a restart. Anything account-derived that is loaded once and cached must be cleared there, and its in-flight fetch cancelled or generation-checked, because a response for the previous account landing after the reset puts it straight back.

**The process-wide stores are re-pointed before the switch is announced.** [scar, September 2026] ViewModels collect `activeProfileId` on `Dispatchers.Main.immediate`, so a switch made on the main thread runs their reset handlers *inline*, inside the `StateFlow` write - before anything after `setActive` has happened. The profile-scoped stores used to be reloaded after it, so those handlers read the previous profile's likes and subscriptions. `ProfileManager.setActive` therefore takes a `beforePublish` hook, run after the stored id changes and before the flow emits, and every path that changes the active profile passes `AccountSwitcher.prepareForActiveProfile`: `switchTo`, `remove`, and `SessionManager`'s `startSession` and `clearSession`. **The last two used to skip the invalidation entirely**: signing in from "No account" or signing out left every process-wide store holding the old profile's data, and its next write stored that data under the new profile's key. A hook must resolve the profile from the stored id (`ProfileManager.activeProfileId(context)`), never from a `ProfileManager` flow, which still names the profile being left. `LikedSongsRepository` also checks before every write that what it holds belongs to the active profile, as a backstop for a future path that forgets.

**Scope of data is a deliberate split: history and taste belong to the profile, the library belongs to the device.** Per profile: local subscriptions and groups, the blocklist, **watch history** (with its removals and resume points), upload mutes, and since September 2026 **listening history, liked songs and search history**. Device-wide: local and saved playlists, hidden playlists, device video playlists, downloads, settings and Last.fm. Everything built from the per-profile stores follows them without a line of its own: Stats, Recently played, Top artists, Recent albums, Most played, Ready offline, Spin, the discovery shelf, the signed-out recommendations and auto-queue (`RecommendationEngine` reads plays, likes and searches on every call), and the fresh-first shuffle's recently-heard set. [scar] Watch history, then listening history, likes and searches were each on the device-wide side until it was noticed that every profile saw, and was recommended from, every other profile's activity. Keys and file names are resolved on every read and write, never captured, because instances outlive a switch; the stores with process-wide flows (subscriptions, blocklist, watch history, upload mutes, likes) are reloaded by `prepareForActiveProfile`, while listening and search history are read from disk each time and need nothing.

**Who kept the data that was already there differs by store, and it matters.** Subscriptions, blocklist, watch history and mutes use `profileScopedKey(base, id, legacyProfileId)`: the profile migrated from a pre-profiles install keeps the un-suffixed keys. Listening history, likes and searches use `historyScopedKey` / `historyScopedFileName` with `historyOwnerProfileId` instead - the profile that was **active on the first run of the build that scoped them**, recorded once in the credential store (never backed up, so a restore cannot rewrite it). [scar] They could not reuse the legacy rule: signing in from "No account" creates a new profile, so on most signed-in installs the legacy profile is a "No account" row nobody opens, and keying on it would have moved everyone's history and likes onto it. The owner keeps `play_history.json`, `liked_songs_meta.json` and the un-suffixed pref keys, which is also what an older build reads after a downgrade; every other profile gets `play_history_<id>.json` and friends. No file is moved or deleted by the upgrade. A file name built from a profile id is restricted to UUID characters, because a restored profile keeps whatever id its backup file claimed.

**Signing in from a device-only profile copies it.** Both sign-in paths create a new YouTube profile when a local one is active (`SessionManager.startSession`, and "Add YouTube account" through `addYouTubeProfileAndSwitch`), and to the person signing in nothing should have gone anywhere. So a **brand-new** profile made from a local one starts with a copy of every per-profile store (`AccountSwitcher.copyProfileScopedData`); the local profile keeps its own. Adding an account from a YouTube profile is a second account and starts empty, and a sign-in that matches a profile already in the roster copies nothing. The copy only ever writes keys the target does not have, and files go through a `.partial` rename, so it can add data but never replace any. **A new per-profile store goes in three places**: `prepareForActiveProfile` if its state is process-wide, `copyProfileScopedData`, and `BackupRepository.collectProfileData` / `restoreProfileData`. Nothing compile-fails when one is missed.

**`Profile.datasyncId`** is YouTube's own account id (`responseContext.mainAppWebResponseContext.datasyncId`, present on every authenticated response [verified August 2026 across `account_menu`, `FEsubscriptions`, `FEwhat_to_watch`, identical in all three]). [scar] Nothing wrote it until the backup work, so `addYouTubeProfile`'s dedupe had never once fired and signing back into an account already in the roster silently added a duplicate row. It is **null until the first authenticated call lands**, so anything matching on it needs a null path.

**A YouTube profile with no stored cookies is a different state from an expired one, and the switcher says so.** `expired` means YouTube rejected a session that still exists and can be refreshed; no session at all means it has never been signed into here, which is what every backup-restored profile is. [scar] **Both taps must actually reach the sign-in flow** - the row promised a reconnect while `onClick` only switched profiles, so tapping the already-active profile did nothing. Reconnecting goes through `onReconnectProfile` with `addAsNewProfile = false`, never the add path: adding captures the session into a *new* profile, stranding the existing one's subscriptions and blocklist on an id nothing is active on.

Removing a profile deletes its cookies but leaves its per-profile data in place: the id is never reissued, so the data is unreachable either way, and a mis-tap should not be able to destroy anything.

Two more: **adding an account must clear the WebView cookie jar first** (Google's login page auto-continues as whoever the jar holds, so otherwise a second account silently hands back the first; stored sessions are untouched by the wipe), and **signing out of the last profile disconnects the account in place rather than deleting the row**, keeping the id so device-local subscriptions and blocklist survive - they never needed an account. Playback deliberately continues across a switch; streams are already resolved, and killing someone's music because they checked another account is a bad trade.

**Profiles can also be switched, added and reconnected from Settings.** [October 2026] The Account page (`ui/settings/AccountSettings.kt`, see `settings.md`) lists the roster and hosts the same `AccountSwitcherSheet`, with the same two paths kept apart: add is a new profile, reconnect lands on the active one. The notification inbox's history (`NotificationHistoryStore`) is keyed by profile id but is a cache of an account's inbox rather than a profile-scoped store: it is not reloaded by `prepareForActiveProfile`, not copied by `copyProfileScopedData` and not in the backup, and a profile that is removed simply leaves its entries unreachable.

## Incognito

`data/IncognitoMode.kt`, toggled from the account sheet, off by default.

**Gated at each write, never at the call sites.** `VideoHistoryRepository.addVideo`, `SearchHistoryRepository.addQuery`, `StatsRepository.addPlayEvent` and both of `PlaybackHistory`'s playback reporters check it themselves, so a sixth surface that records something inherits the behaviour instead of having to remember. That is the whole reason it is process-wide state rather than a flag on a ViewModel.

**It suppresses recording, not doing.** Playback, downloads, playlists, likes and subscriptions are untouched, and the row's subtitle says so. [judgement] Someone reading "incognito" as "nothing I do is saved" would be surprised by a download appearing later, and silently discarding a save the user asked for by name is a different feature wearing this one's label.

**Persisted rather than held in memory, so it fails closed.** A service restarted after the app was evicted must not start recording again on its own. The preference is written before the in-memory flag for the same reason - the reverse order records nothing this session and everything after the next process death. It is excluded from backups because it describes a session.

**The indicator is not optional.** A badge on the avatar whenever it is on, because a mode that silently stops recording is a promise, and a promise whose state cannot be seen is one someone will assume is off at the wrong moment.

## Backup and restore

One versioned zip holding the whole install (`data/BackupTransfer.kt`, `BackupRepository.kt`, `ui/settings/BackupScreen.kt`). Not interoperable and not trying to be - `SubscriptionTransfer` is the interoperable one.

**A backup copies the stores, it does not serialize the models.** `BackupRepository` holds three allowlists - preference *files*, `filesDir` directories, `filesDir` files - and a preference file is copied key by key, so every setting added from now on lands in backups free. The cost, stated where it is paid: **the allowlists restate names that are private constants in the stores that own them, and no compiler checks that.** Rename a preference file or stored file and it silently drops out of every backup taken afterwards.

**The exclusions are deliberate.** Session cookies (a credential, and the file is meant to be safe in Drive), `visitorData` (carrying one device's onto another is the flagged-token case), the download-migration flag (a restored `true` permanently skips a migration that never ran), the last-played snapshot and both playback-session files, and the incognito flag (they describe a session, not a preference - a restored incognito would silently stop a second device recording history for a reason its owner never chose), and downloads - the media is far too large and its metadata without the media is a library of broken rows.

**The profile split is carried structurally**, because raw keys would not survive the trip: `profileScopedKey` suffixes with a device-local UUID except for the legacy-migrated profile, so a raw `subscriptions` key restored elsewhere lands on whichever profile happens to be that device's legacy one. Local subscriptions, the blocklist, **watch history** (including its per-video resume positions, which live in the same preference file and are scoped the same way), upload mutes, and from format 2 **listening history, liked songs and search history** are keyed by *backup* profile id in the file, and the restore recomputes the real key with the receiving device's legacy or history-owner id after resolving each backup profile to a local one - by id first, then by `datasyncId`. **Format 2** (September 2026) exists because a version-1 reader would restore a file with per-profile history as one with no history at all, silently, so older builds now refuse it. A version-1 file's device-wide copy of the three lands on the profile the restore lands on, the rule the upgrade followed; it carries no mute lists, so for those the mutes already on the device are left alone. The restore writes only allowlisted `files/` entries, since a version-1 file also holds `play_history.json` and `liked_songs_meta.json`, which written raw would go to whichever profile owns the un-suffixed names. History moved onto this path the day it became profile-scoped, and the `video_history` entry came out of `PREFERENCE_FILES` in the same change: a profile-scoped store left in the raw copy is the failure that paragraph describes, and nothing compile-fails when one is. The watch-history count in the manifest sums the per-profile entries for the same reason - read out of the raw preference map it would silently report zero. `ProfileManager.restoreProfiles` is the only place a profile is created with an id rather than a fresh UUID, and it has to be: a restored profile with a new id is an identity with none of its own data.

**Restore replaces the allowlists, merges the roster, and restarts the process.** Merging is the one exception, because a profile already here holds cookies the file does not, and signing someone out of an account they are using is not something a restore should do; restored YouTube profiles come back `expired = true`, which already means "this is the account, sign in again". The restart exists because with no DI a restore cannot reach what it just invalidated - per-instance `ThemePreferences` flows, the process-wide companion caches, `MusicService`'s own repository, and SharedPreferences' in-memory map. **Every write on the restore path is `commit()`, never `apply()`**, since the process is killed deliberately and a queued write dies with it; hence the `commitNow` parameter rather than switching wholesale. `BackupTransfer` is format only and touches no Context, so its edge cases can be reasoned about without a device. Zip rather than one JSON document because playlist covers are binary and a chosen one is an irreplaceable photo, and because a full play history compresses hard. Entry sizes are bounded and entry names are never used to build a path.

**Last.fm is a separate device-wide identity.** Its encrypted session, account cache, pending authorization and queue are excluded from Android and Koda backups. Incognito cancels Last.fm calls and stops new listening qualification; disconnect erases the account locally. See `lastfm.md`. [judgement September 2026]

**Scheduled backups (`work/ScheduledBackupWorker.kt`) only ever write.** [judgement] Restore stays user-initiated, since an unattended restore would replace an install nobody asked it to touch. Pruning happens only after the new archive is written and flushed. Lost folder access raises a notification that opens the page (`navigate_to`) rather than failing silently. `ScheduledBackupRepository` keeps its own preference file outside `BackupRepository.PREFERENCE_FILES`, because a folder grant and a schedule belong to one device.

**Stated taste is the fourteenth process-wide store and a per-profile one.** [October 2026] `TasteProfileStore` (prefs `taste_profile`, key through `historyScopedKey`, so the profile that kept the history keeps this) holds picked and followed artists, genres and deck songs. It is reloaded in `prepareForActiveProfile`, copied in `copyProfileScopedData`, and carried as `tasteProfile` in `BackupProfileData`; a backup without the field leaves existing taste alone rather than clearing it. `setupSeen` in the same file is device-wide and outside the backup. Its two key names were renamed once before release and are frozen from the first release on.

**A Koda profile is a device-only profile with a face.** [judgement October 2026] `ProfileKind.LOCAL` was always a first-class identity; it now looks like one. `KodaAvatar` (`data/KodaProfile.kt`) is six indices - shape, colourway, eyes, mouth, extra, blush - drawn by `KodaAvatarView` as fractions of its own size, so it is right at 28dp and at 148dp and a new option is a number, not an asset. Indices are stored: append, never insert or reorder; an index past the end wraps, so a newer build's avatar still draws on an older one. The colourways are literal colours, the third exception to the no-hardcoded-colour rule (`docs/rules.md`). A profile that has chosen nothing wears `KodaAvatar.forSeed(id)`, so a local profile is never the grey person icon. A photo is copied into `filesDir/profile_photos/` as a 512px square and wins over the avatar; the path is reused per profile, so `photoVersion` is the image cache key. `KodaProfileStore` is the fifteenth process-wide store (the picture changed on the profile screen has to change on Home's top bar) and is device-wide, keyed by profile id, because it describes the whole roster. **It is not in the backup yet**, and the account switcher sheet still draws its own pictures rather than `ProfileAvatar`. Renaming goes through `ProfileManager.updateIdentity`.

**The profile screen** (`ui/profile/KodaProfileScreen.kt`) is hosted in `HomeScreen` as an overlay rather than a route, because the switcher sheet it hands to lives there. Tap the profile picture in music mode to open it; a long press is the switcher (`LocalOpenAccountSwitcher`), and video mode keeps the tap as the switcher. It reads the active profile's history, likes and stated taste and makes no request except a top artist's picture, through `ArtistPhotoCache` and Home's exact-name rule. Editing is offered only on a local profile: an account's name and picture are YouTube's.
