# Subscriptions and the blocklist

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

**Two stores, one button.** **Account subscriptions** are the signed-in account's, read from `FEchannels`, written with `subscription/subscribe`. **Local subscriptions** are device-only (`data/LocalSubscriptionsRepository.kt`, prefs `local_subscriptions`) and never visible to YouTube.

**`data/SubscriptionActions.kt` is the only place that decides what a Subscribe tap means.** Three ViewModels drive that button - video player, Shorts, `ChannelViewModel`. Subscribing writes wherever `ThemePreferences.subscribeTarget` says; on `auto`, the account when signed in and the device otherwise. **Unsubscribing ignores the target and clears both stores**: a toggle that turned off in one place and left the channel followed in the other leaves the button reading "Subscribe" for a channel the user still follows, which is the UI lying. The sign-in wall appears only when the user explicitly chose the account target, which is why `requireSubscribeLogin` exists separately from `requireLogin`. The button binds to `isSubscribedToChannel` (account OR device), never `engagement.isSubscribed`, which only knows about the account.

**The local feed is built from each channel's Atom feed, not InnerTube.** Nobody assembles a device-local feed server side, so `getLocalSubscriptionsFeed` merges one request per followed channel, which makes the per-channel source the whole decision. The feed is ~50 KB against roughly 1 MB for the equivalent browse (10 MB versus 200 MB on a 200-channel refresh), needs no client version, cookies or visitorData, and is the only one of the two carrying a real ISO timestamp - InnerTube only says "3 days ago", and merging fifteen channels on prose that coarse shuffles the top arbitrarily. Hence `VideoItem.publishedAtMs` as the merge key. What RSS lacks is duration and live status, which is the trade the "Fast Subscription Refresh" setting states out loud.

**Fast mode means "RSS, else browse".** [verified August 2026] Some channels answer their own advertised `rssUrl` with a 404 despite plenty of uploads, while others served fine from the same IP seconds later. Treating that as "no uploads" drops the channel silently and, for someone following a handful, empties the tab and reads as a network failure. So `getLocalSubscriptionsFeed` falls back to `channelVideosWithTimestamps` per channel, costing a request only where needed. **Do not optimise that fallback away** - but see `youtube-data.md` for the 429 exception, which is the one refusal it must not answer. Fetches run `FEED_CONCURRENCY` (6) at a time; unbounded would mean hundreds of sockets on a pull-to-refresh, and `UploadCheckWorker` needs the same ceiling for the same reason. **The parser must stay namespace-unaware** (`XmlPullParserFactory` with `isNamespaceAware = false`, *not* `android.util.Xml.newPullParser()`, which turns namespaces on), with prefixes stripped so the Atom `<title>` and Media RSS `<media:title>` collapse onto one local name. The empty-feed message blames the connection only when there genuinely is no network.

**The channel rail is a filter, not navigation.** Ordered by the newest upload each channel has in the current merged feed, with channels absent from that snapshot following alphabetically - derived locally rather than trusting an undocumented order from the subscription-list response. Tapping an avatar selects that creator and loads their Videos tab into the feed below; filtering only the merged snapshot would be wrong because a followed channel can have hundreds of uploads and nothing in it. Feed controls filter by upload age and reverse order without refetching, and offer no local Live or Shorts filter because fast RSS carries neither.

**Import/export** (`data/SubscriptionTransfer.kt`): NewPipe/PipePipe/Tubular `subscriptions.json`, the same family's backup archive (`PipePipeData-*.zip` / `NewPipeData-*.zip`), Takeout `subscriptions.csv`, and OPML - **sniffed by content**, not by extension or MIME type, both of which providers lie about. The backup archive matters because PipePipe's obvious menu entry ("Export Data") produces the zip, so that is what people arrive with. Inside is the app's whole Room database, read directly [verified August 2026]: `subscriptions(uid, service_id, url, name, avatar_url)` plus `feed_group` / `feed_group_subscription_join`. SQLite needs a real path, so `read()` takes a scratch `File`; entry names are never used to build it. Every column but `url` is optional, since the forks differ by schema revision. This is the only import path carrying avatars, so those channels skip the backfill. Non-YouTube `service_id` entries are dropped but counted, so a PipePipe user is told why 40 of their 200 did not come across. Handles and vanity URLs resolve to canonical UC ids through `navigation/resolve_url` (works signed out) and are never stored unresolved, because every other call keys off the UC id. Export writes the NewPipe-compatible shape; Koda's groups ride along under a `groups` key those apps ignore.

The Subscriptions tab (`ui/video/SubscriptionsContent.kt`) has no hard sign-in wall. It blocks only when nothing is followed anywhere, and offers importing as a peer of signing in. Tapping a channel opens the real channel page. `HomeViewModel.logout()` must clear `_accountChannels` explicitly - the tab no longer empties itself on sign-out, so stale account channels would sit there unreachable.

## "Don't recommend"

`data/NotInterestedRepository.kt` holds hidden video ids and blocked channels (prefs `not_interested`), process-wide.

**It is the engine of the feature, not a cache in front of YouTube's.** [verified August 2026] Signed out, InnerTube returns no `feedbackToken` anywhere - not on watch-next, browse or search - because there is no account to record against. It is also the only half that acts immediately; YouTube's own feedback is advisory and takes days.

**Signed in, the dismissal is also sent** (`sendDismissalFeedback` → `youtubei/v1/feedback`), so it cleans up recommendations on youtube.com too. `data/NotInterestedActions.kt` is the one place that decides what a dismissal means: the local hide first and synchronously, the account call fire-and-forget on the caller's scope with its result dropped. It must stay that way - the hide has already happened, nothing waits on the network, nothing rolls back on failure. Tokens ride on `VideoItem.dismissal` because they are single-use and bound to the response that carried them; they are null for RSS, NewPipe and every signed-out item, so propagation is skipped rather than failed.

[verified August 2026] `/next` and `FEwhat_to_watch` lockups carry both "Not interested" and "Don't recommend channel"; `FEsubscriptions` carries only the video hide; **search carries no tokens at all**. The two entries are told apart by `leadingImage`'s `clientResource.imageName` (`NOT_INTERESTED` versus `REMOVE`), **never by the visible label** - that string is localized and differs per surface. YouTube pre-bakes an `undoFeedbackEndpoint.undoToken` into the same response, carried on `UndoableAction.undoToken`. Success is `feedbackResponses[0].isProcessed`, not the HTTP code; like `subscription/subscribe`, this endpoint answers 200 to requests it did not act on.

**Filtering is a derived flow over the raw fetch**, never a write into it. A tap removes the item next frame with no refetch and Undo restores it in place; mutating the fetched list would make undo a refetch that brings the video back somewhere else or not at all. Autoplay-next reads the *filtered* list. Blocking a prolific channel can gut a grid and scroll-triggered load-more cannot fire with nothing to scroll, so a cut below `FEED_TOP_UP_THRESHOLD` requests another page. **Shorts are the exception and filter on ingestion**, because the pager index and `playIndex` both address `_shorts` positionally and a filtered view layered on top would put the pager on item N of one list and playback on item N of another.

**Music mode shares this store, and shares it deliberately.** A YouTube song *is* a video keyed by the same id, so "don't recommend this" said in either mode is the same sentence about the same thing and two sets would let one mode go on recommending what the other was told to drop. `hideSong` writes an ordinary hidden entry; `blockArtist` writes a `BlockedChannel` with a **blank id and the artist's name**, leaning on the name fallback `isFiltered` already has for lockups that omit a channel id - a [Song] carries no artist id, only a name. Matching is whole-string and case-insensitive, never substring, or blocking "Sam" takes "Samantha" with it. The music half is **local only and always will be**: no music feed response Koda parses carries a dismissal token, so there is nothing to propagate - the position every signed-out video dismissal is already in. `HomeViewModel.youtubeSongs` filters through it as a derived flow over the raw fetch; **`songs` (the device library) never does**, because "stop recommending this to me" was never a request to hide the user's own files, and the long-press rows are offered only on `SongSource.YOUTUBE`. The player's overflow offers the artist block but not the song hide, matching what video mode's player does for the same reason: the store is a recommendation filter, not a skip list.

Per-surface rules follow the tokens and YouTube's own menus: search offers only the channel block; the Subscriptions feed offers only the video hide (blocking a channel you deliberately follow, from the feed that exists to show it, is a contradiction - unfollow is the tool); the player hides "not interested" for the playing video. Undo is a single app-wide `SnackbarHost` at the root of `MainActivity` - the action comes from five surfaces, two of them overlays above the NavHost, so a per-screen snackbar would be hidden behind the Shorts overlay exactly when needed. That host lives for the whole app, so its `YouTubeRepository` is built lazily (it carries an OkHttp pool and opens EncryptedSharedPreferences). The undo request runs on a `rememberCoroutineScope`, not the snackbar's `LaunchedEffect`, which is cancelled the moment another dismissal replaces it. `NotInterestedScreen` is the permanent list; without it a mis-tap weeks ago is an invisible, unfixable hole in the feed.
