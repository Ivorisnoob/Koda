# Settings

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

General app settings live in `data/ThemePreferences.kt` (prefs `ivor_music_theme_prefs`, one `MutableStateFlow` plus KEY constant plus private getter plus public setter each). A new general setting threads through **five files**; Last.fm's account/session controls use the separate encrypted store described below:

1. `ThemePreferences` - StateFlow, KEY, getter/setter.
2. `ui/theme/ThemeViewModel.kt` - the flow plus a `setX()` delegate.
3. `MainActivity.kt` - collect in `setContent`, add a param pair to `MusicApp`, pass through to `SettingsScreen` (threaded twice).
4. `ui/settings/SettingsScreen.kt` - new params, passed to whichever page owns it.
5. `ui/settings/SettingsPages.kt` - the actual row.

**A new string goes in `values/strings.xml` and stops there.** [verified September 2026] The base file carries 1,039 strings; each of the 25 `values-*` locales carries 182. They are partial by design - the most visible strings only - so an English-only addition is the normal case and Android falls back to it cleanly. Do **not** sweep a new key across 25 files by hand, and do not avoid adding a string that the UI needs because of an imagined translation cost. The locale sweep in `workflow.md` is for the rare case where a string is deliberately being translated everywhere, and it is the user's call, not an automatic obligation. Reuse an existing string when one already says exactly the right thing (`action_share`, `cd_more_options`, `ar_start_radio` all earned their keep this way); do not reuse one that nearly does, because the next person changes it for its original caller.

**Then add it to `buildSettingsSearchIndex` in `SettingsSearch.kt`.** A setting missing from the index is unfindable and there is no compile error. That is the one omission here that fails silently. **Backups need nothing** - `BackupRepository` copies the whole prefs file key by key.

**Settings is a hub and eleven detail pages, not one scroll.** `SettingsScreen.kt` holds the hub, the page router and every dialog; `SettingsPages.kt` the pages; `SettingsComponents.kt` the shared rows; `SettingsSearch.kt` the index and matcher. Pages are a `SettingsPage` enum driven by `AnimatedContent`, **not** nav routes: `SettingsScreen` takes 112 parameters [drifts] and a destination per category would repeat that list twelve times.

**A page big enough to own a file gets one.** `DISPLAY_SIZE` lives in `ui/settings/DisplaySizeSettings.kt` and `SPONSORBLOCK` in `ui/settings/SponsorBlockSettings.kt`, rather than in `SettingsPages.kt`. `DISPLAY_SIZE` is reached from a row on Appearance rather than the hub, because it is one setting rather than a category; `SPONSORBLOCK` earns a hub row of its own because it is eight categories with three states each. Its back goes to Appearance, not the hub - it is opened from there and the value is usually adjusted more than once. A page that is really one control with a preview is the case for this shape; a page that is a list of rows belongs in `SettingsPages.kt` with the rest. Back unwinds one step at a time - open page, hub, clear the query, leave.

**The App icon page owns a file and a pinned header** (`ui/settings/AppIconSettings.kt`, model and renderer in `ui/settings/AppIcon.kt`, storage in `data/AppIconStyleStore.kt`). It earns both: it is nine presets, six shapes and four colour rows, all judged by looking at one preview, so `SettingsDetailScaffold` takes an optional `header` slot that sits between the top bar and the list and does not scroll - a preview inside the list is gone by the time anyone reaches the swatches. **Selecting is not applying**: a preset tap loads the preview and one contextual action in the header commits it, because applying on tap changed the home-screen icon once per browsed preset. `AppIconManager` builds its component names from the alias classes' own package rather than from `applicationId` - see the silent-failure index in `CLAUDE.md` - enables the incoming alias before disabling the outgoing one, and returns whether the change took so the caller cannot write a preference for something PackageManager refused. Saved styles live in their own preference file and are therefore in backups; `IconShape` ids and `SavedIconStyle` field names are persisted and frozen.

**The updater reports a hand-off, never a download it does not own.** `ui/settings/UpdateScreen.kt` is a `NavHost` route; About is `ExpressiveAboutDialog` inside `SettingsScreen.kt`. Koda holds no `REQUEST_INSTALL_PACKAGES` permission and writes no APK: the download button fires `ACTION_VIEW` on the GitHub asset URL and the browser plus the platform installer do the rest. That is the security posture, not an unfinished feature, so an in-app downloader or installer is a different decision with a different threat model rather than a natural next step. What the screen owes the user is the truth about the tap - `openExternal` returns whether an activity took the intent, a started download is acknowledged by file name, and a device with no handler says so instead of leaving a button that appears broken.

**Local Only is a state of the update screen, not a replacement for it.** [scar] The route used to swap in a full-screen `LocalOnlyNotice`, which hid the installed version, build, build type, Android version and ABI - every one of them already on the device and needing no connection - behind a page with no visible back control. `UpdateScreen` takes `localOnlyMode` and renders `UpdateResult.LocalOnly` where the network result would sit, keeping the top bar and the installed-build card. The preference is a `LaunchedEffect` key rather than an early return, so turning it off starts the check that was refused and turning it on stops offering a release that cannot be fetched. The repository never returns `LocalOnly` - it holds no Context - which is why the decision belongs to the screen. `LocalOnlyNotice` remains correct for the video tabs, where there is genuinely nothing local to show.

Rows to copy, all in `SettingsComponents.kt`: `SettingsRow`, `SettingsToggleRow` (whole row is the hit target), `SettingsHubRow` (category plus live value), `SettingsCard`, `SettingsSection`, `SettingsDivider`, `SettingsDetailScaffold`. They read colors from the theme - do not add `textColor`/`accentColor` parameters back. Destructive rows take `SettingsRowDefaults.destructiveTint`. **Every hub row shows the live value of what is inside it** ("Dark, Vibrant", "412 MB cached"); a category row without one is a worse version of the flat list this replaced. Dialogs stay hosted by `SettingsScreen` and are opened by pages through callbacks, because a dialog owned by a page dies with the page transition. `AlertDialog` with `containerColor = surfaceContainerHigh`, `RoundedCornerShape(32.dp)`, 64dp rounded icon box, spring `scaleIn` via `AnimatedVisibility`.

Theming beyond light/dark: `color_palette` (default `dynamic`) chooses between wallpaper-based dynamic color and the fixed palettes in `ui/theme/ColorPalettes.kt`, applied in `ui/theme/Theme.kt`. `palette_style` (stable storage ids, default `tonal_spot`) selects Tonal Spot, Vibrant, Expressive, Fruit Salad or Monochrome for presets. `PaletteStyle.kt` resolves every Compose role through Material's HCT utilities, including surfaces and fixed roles; do not restore the old HSL accent-only overlay. Wallpaper retains the system scheme, Black/White retain their dedicated container fills, and AMOLED runs last. Both the app and widgets use the same resolver; picker previews use the same preset generation plus AMOLED. The style control lives inside `ColorPaletteScreen`, reached from Appearance's existing palette row and its own settings-search entry. [verified September 2026 against Material 1.12's AAR] Role access uses `MaterialDynamicColors`, since that version's `DynamicScheme` has no role getters.

**Defaults worth knowing.** The player style defaults to `EDITORIAL`, and the device music library (`load_local_songs`) defaults to **off** - the audio permission request is triggered by that setting being on, so a default of on met anyone skipping onboarding with a system dialog for a feature they never asked for. `migrateLoadLocalSongsDefault()` keeps existing installs on the old `true`: the Settings toggle is the only writer of that key, so an upgrading user who never opened that screen has nothing stored and would otherwise find their library emptied. It needs its own one-shot marker rather than a lazy check, because `onboarding_completed` flips to true for fresh users too.

**Lyrics owns a hub page** (`LyricsSettings.kt`). [judgement September 2026] `LyricsConfiguration` is one atomic settings snapshot: provider order, excluded providers, online lookup, timing preference and plain-text eligibility. A compact connected provider list uses the shared queue drag engine, commits order on release, and offers move-up/down accessibility actions. Matching uses the same connected choice buttons as Display Size and SponsorBlock. The detail scaffold accepts optional list state and item spacing for this list; existing pages keep their defaults. The hub reports the enabled count and first source; search indexes all seven names. Changes apply on the next lookup.

**Last.fm owns a dedicated page** (`LastFmSettings.kt`) and a searchable hub row. Its ViewModel observes the shared Last.fm account coordinator, rather than threading credentials through the theme settings contract. The master switch belongs to the encrypted account/session store and is deliberately excluded from backups. See `lastfm.md` for authentication, sync, and verification limits.
