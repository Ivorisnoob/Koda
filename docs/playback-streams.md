# Stream resolution, caching and quality (music and video)

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

**A NewPipe extraction is blocking, so its caller must bound the wait rather than the work.** [scar] One `fetchPage()` is eight sequential HTTP requests [verified September 2026: an ANDROID `visitor_id`, `reel/reel_item_watch`, a visionOS `visitor_id` and `/player`, `sw.js`, a WEB `visitor_id`, the WEB metadata `/player`, and `/next`], each one blocking inside `Downloader.execute()`. Two consequences that together turned "slow" into "the song will not play, and skipping does not help". The downloader ran on the general 30s connect/read client with **no `callTimeout`**, so nothing capped a single request in wall-clock terms; and `MusicService`'s `withTimeoutOrNull(RESOLVE_TIMEOUT_MS)` could not fire, because a `coroutineScope` does not return while an uninterruptible child is still inside a blocking call - so the timeout that was supposed to reach the InnerTube fallback instead waited for the very extraction it was abandoning, ran out, and resolved the song to `error://resolution_failed`, which the player answers by skipping. `NewPipeAudioSource.withinBudget` starts the extraction on `NewPipeGateway.newPipeScope` - deliberately **not** a child of the caller - and bounds only the `await()`, so the fallback starts on time while the orphan finishes or dies against `YouTubeHttp.newPipeClient`'s per-request cap. The cap is generous on purpose: the same downloader serves search, playlists and channel pages, and tightening it to the playback budget would fail those on a slow connection to fix a problem the budget already fixes. **Anything else that wraps a blocking extractor call in a coroutine timeout has the same non-fix** unless it detaches the work the same way.

**`catch (e: Exception)` in the resolution path is the general trap with a specific cost.** Swallowing `CancellationException` there reports a cancelled call as "this client has no streams", which sends the chain on to the next client inside a coroutine that is already dead - so a single timeout burned NewPipe *and* both InnerTube clients and still returned nothing. `NewPipeAudioSource` and `PlayerApi.player` rethrow it ahead of the general catch. [verified October 2026] Every general catch under `data/youtube` and `data/stream` was audited by script: one is a risk only when its `try` body can suspend, since a body that merely blocks inside OkHttp never sees a cancellation. Six did (the three fallbacks of `getTrendingVideos`, the local subscriptions feed, the channel profile backfill, `getCaptionTracks`) and now rethrow. A new `catch (e: Exception)` around a suspending call needs the same.

**Music stream resolution is a single-flight, but no resolution work may run inside a `ConcurrentHashMap.compute*` callback.** [scar] A download, valid in-memory URI or fully cached song can finish before `getOrStartResolution` has even returned. The old `computeIfAbsent` mapping function registered `invokeOnCompletion { map.remove(id) }`; when that fast result had already completed, coroutine registration invoked the cleanup synchronously from inside the map computation and Android's `ConcurrentHashMap` threw `IllegalStateException: Recursive update` on the main thread. `DeferredSingleFlight` publishes a lazy deferred with `putIfAbsent`, registers conditional cleanup, and only then starts it. Preserve that order, and preserve `remove(key, deferred)`: an older forgotten resolution must not remove its replacement.

**All googlevideo media goes through bounded ranged requests.** [measured July 2026: 32 KB/s open-ended versus 5-22 MB/s bounded on the same URL] googlevideo paces open-ended progressive requests to roughly the media bitrate, which reads as "slow loading on a good network". Playback uses `data/ChunkedStreamDataSource` (10 MB chunks plus per-URL UA, wired via `CacheManager.createPerClientHttpFactory()` and the video VMs' `streamDataSourceFactory`); `DownloadRepository.downloadStream` runs its own ranged loop, into a session checkpoint rather than straight into the target, which is what makes a download pausable: `data/DownloadCheckpoints.kt` keys a partial file by request, role and rendition identity (`videoPlaybackCacheKey`, so a re-signed URL for the same itag resumes rather than restarting), and a paused entry keeps its progress row and its bytes while leaving the queue. Checkpoints are session-scoped and the directory is emptied on construction: an orphan from a killed process has no request to resume it and must not hold storage forever. A resumed request re-enters the queue carrying its own byte counts, since a bar that resets to zero over a half-finished file reports the opposite of what happened. `MusicService.prefetchUpcomingSongs` additionally pre-caches the first 512 KB of the next 3 queue songs (`warmStreamCache`) so skips start from disk. **Music and video use different caches.** [scar] The old shared size-bounded `SimpleCache` let one high-bitrate video consume a user's entire music cache limit and evict songs, while a 4K video larger than the limit continually evicted its own beginning. Music keeps the adjustable LRU and is the only cache shown in Settings and Ready offline. Video and Shorts use an uncapped transient `SimpleCache` that clears five minutes after the last video surface closes; a full disk degrades to direct playback through `FLAG_IGNORE_CACHE_ON_ERROR`. Old `video-playback:` and opaque video entries are removed from the music LRU on process start. Progressive VOD keeps stable `video-playback:<videoId>:<role>:<itag>` keys, with separate video/audio/muxed roles so split sources and qualities cannot mix bytes. Local Only is enforced in the upstream `ChunkedStreamDataSource`, below both cache pipelines, so cached spans and device files remain readable while the first cache miss is refused.

**Caching is three switches and preloading is a fourth, and switching one off must not lose what is already stored.** Music, video and Shorts each have their own toggle because they cost differently and are wanted differently - a metered connection wants the 4K scrubbing buffer gone and the music cache kept. Turning one off swaps that pipeline to a **read-only** cache source (`setCacheWriteDataSinkFactory(null)`) rather than to the direct source: the bytes already on disk are still the fastest way to serve a replay, and a switch that silently made previously cached media re-download would be a worse deal than it sounds. Video and Shorts share one store and are told apart by a `shorts:` key prefix (`playbackCacheCategoryKey`), which is what lets either be cleared without touching the other; that prefix is why `isShortsCacheKey` exists and why a shorts key is not a `video-playback:` key to anything matching on that prefix. The preload switch gates work rather than storage - `MusicService.prefetchUpcomingSongs`, `warmStreamCache`, the Shorts ladder resolution and its range warm - so someone can keep replay caching and still stop the app spending data on media they have not asked for.

**Nothing in the adaptive pipeline may be served from a playback cache, and the switches are no escape from that.** [scar] Every network fetch the video player makes goes through `SwitchingPlaybackDataSource`, and the HLS/DASH branch of `loadQuality` hands the player a bare `MediaItem` with no custom cache key - so the manifest and every media playlist were stored under `opaquePlaybackCacheKey(uri)` like any other bytes. An HLS media playlist is re-fetched from the *same* URL every target duration, and that reload is the only way the player learns a broadcast has produced new segments: Media3 asks for it with an ordinary cacheable DataSpec (FLAG_ALLOW_GZIP, no key) and `CacheDataSource` resolves the unset length out of the stored content metadata and reads the first copy back off disk [verified September 2026 against 1.11's `DefaultHlsPlaylistTracker` and `CacheDataSource` bytecode]. So the segment list froze at whatever the first fetch held. **The signature is the asymmetry**: a live stream played the handful of segments it opened with and then stalled at the live edge, while seeking back into the DVR window went on working, because those segments were already listed in the frozen copy - which is exactly how it was reported. Turning video caching off would not have fixed it either, since read-only still *reads* what is stored. `isUncacheablePlaybackUrl` (`data/VideoPlaybackCache.kt`) routes the whole adaptive pipeline straight to the direct source, and it is one predicate shared with `ChunkedStreamDataSource.shouldChunk` because both are asking the same question. It excludes live *segments* as well as playlists on purpose: the video cache has no byte ceiling and an hour of a broadcast is an hour of media nobody replays.

**Seek latency is set by the load control and the seek parameters, not by the disk cache.** [scar] The seek bar's pale segment is `player.bufferedPosition` - ExoPlayer's in-memory sample queue - so `DefaultLoadControl` *is* the RAM cache for video, and the disk cache only backs its misses. Two defaults made a scrub stall even when every byte was already in RAM. `bufferForPlaybackAfterRebufferMs` was 2.5s: a seek out of the buffered region counts as a rebuffer, so the first frame was withheld until 2.5s of media had been queued regardless of where the bytes came from. And ExoPlayer seeks exactly by default, decoding from the preceding sync sample and discarding every frame up to the target - hundreds of them on a 1080p60 multi-second GOP, again paid on cache hits and network fetches alike. Scrub-bar drags and the 10s steps now pass `SeekParameters.CLOSEST_SYNC` through `seekPlayerTo`, which renders the nearest keyframe; chapter starts, comment timestamps and every session or quality-switch restore pass `precise = true` and keep `EXACT`, because those address a specific moment and landing half a GOP away is wrong. The back buffer is 45s rather than 15s, since backwards is the common scrub direction and 15s sat inside one drag. The 96MB allocator ceiling is shared by a split pair's video and audio sources and by that back buffer, so it - not `maxBufferMs` - is usually what bounds how much of a scrub is served from memory.

**Quality.** `VideoQuality(resolution, url, format, isDASH, audioUrl)` where `resolution` is a YouTube label ("1080p60", "720p"). Both `getVideoStreamsFromNewPipe` and `parseQualitiesFromStreamingData` return highest-first ladders with 60fps before 30fps. Generated NewPipe manifest *content* (`Stream.isUrl == false`) must never reach a Media3 URI source. Starting quality comes from per-network settings (`ThemePreferences.getDefaultVideoQuality()`, a fresh read picking Wi-Fi or mobile via `isActiveNetworkMetered`) through `pickDefaultQuality`: best label at or below target height, else lowest. Music resolution honours per-network music quality the same way (`currentMusicQuality`: high/normal/low). **HDR is opt-in** (`prefer_hdr_video`, default off). The display check beside it (`hasHdrDisplay`) **fails open** [scar]: it was added on top of a preference gate that worked, read `Configuration.isScreenHdr` off the ViewModel's Application context - which is not display-adjusted, so the bit is false on phones with an HDR panel - and silently removed HDR from the quality sheet for everyone who had been using it. It asks `DisplayManager` for the default display's supported HDR types now, and only a display positively confirmed to have none leaves the HDR rungs out; an unanswerable query honours the preference, because withholding a feature somebody deliberately switched on is worse than fetching a ladder that turns out not to help. NewPipe v0.26.5's itag table ends before YouTube's HDR itags 330-337, so it makes the visionOS request and then drops every HDR rendition from its Stream models. The direct visionOS `/player` that `VideoStreamResolver` asks first is parsed by `parseDirectVideoQualities`, which keeps them, so HDR comes from the response that resolved the video and only the NewPipe fallback is without it [verified September 2026: itags 330-337, VP9.2, unciphered URLs, signed out]. HDR and SDR coexist at one label - `VideoQuality.dynamicRange` is part of the dedupe and selection identity, never a variant to collapse. When both ladders exist, the quality sheet separates them into connected HDR and Standard tabs, starting on the range actually playing; an SDR-only ladder keeps the ordinary compact list. The mini player is a TextureView and cannot present HDR, so minimising drops to the matching SDR rung and expanding restores it. Video downloads pick the best MP4 adaptive pair at or below the `VideoDownloadSheet` choice, the request carrying the label so retries keep it. **Music downloads have a quality of their own.** [verified October 2026, visionOS `/player`, signed out] A music id answers with two AAC/M4A audio streams, itag 140 (AAC-LC, about 128 kbps, 44.1 kHz) and itag 139 (HE-AAC, about 48 kbps), each with a plain `url` and a `contentLength`; the Opus streams beside them (249/250/251) are WebM, which the M4A tagging pipeline cannot publish. `getDownloadAudioFormats` reads both from one request, so the sheet shows an exact size on each card without the size probe it used to make. [scar] A download had silently followed the *streaming* quality of whichever network was active, so a song saved on mobile data with streaming on Low was kept at 48 kbps with nothing saying so. `ThemePreferences.currentDownloadMusicQuality` is the default now (`high` / `saver`, stored and frozen) and still answers the old way until a choice is stored, so existing installs do not change. The request carries the quality and whether to keep lyrics (`DownloadRequest.audioQuality`, `saveLyrics`), so a retry keeps both.

**Stream resolution is shared across video surfaces.** `VideoStreamResolutionCache` single-flights NewPipe's blocking `fetchPage()` and keeps at most 16 successful ladders, expiring each at the earliest signed video/audio URL minus five minutes (15 minutes for a URL with no readable expiry). This is why opening the download sheet for the video already playing, or moving between a Short and its watch page, does not extract it again. Empty results are never cached. A source recovery invalidates that video's ladder before retrying; a visitorData remint or profile switch clears every ladder, because returning an old signed URL there would make recovery a no-op. **Inside a resolution, `dropResolved()`, never `clear()`.** [scar, caught before shipping October 2026] `clear()` cancels every resolution in flight, and a video resolution runs inside the cache - so the token check refusing a token mid-resolution would have cancelled the very load it was protecting. `dropResolved()` forgets finished ladders and lets in-flight ones finish uncached; one that was signed under the old token reaches its player, whose 403 recovery traces it to the replaced token and only re-resolves. Each `YouTubeRepository` builds its own `YouTubeHttp`, which keeps its own session and Local Only interceptors but shares one bounded OkHttp dispatcher and connection pool so they reuse threads and sockets.

**Resolved Shorts URLs are not buffered Shorts.** [scar September 2026] The old prefetch resolved two future ladders, warmed bytes only for the immediate next item, then skipped every cached ladder on later swipes. The second item therefore never got its media head warmed when it became next. `ShortsPlayerViewModel` now revisits cached ladders, resolves only the immediate next Short after a 750 ms settling delay, and warms audio plus the first 2 MiB of its video (512 KiB on metered networks). The 256 KiB audio head is fetched first for split renditions. CacheWriter reuses completed ranges, so revisiting a warmed ladder does not redownload it. Metadata has a separate concurrency slot; the stream prefetch waiter is limited to one job. This does not cap shared detached extractions that already started; cancellation cannot interrupt their blocking HTTP work. Jobs outside the nearby window are cancelled, and close/profile/HDR/visitor-token invalidation cancels old work. [judgement September 2026] A 429 hold cancels Shorts prefetch waiters and range warming; queued work rechecks the hold before starting. Already-started shared extraction may finish. No speculative backward extraction is started; swipe-back reuses cached results. Explicit playback stays available. Range warming checks coroutine cancellation and cache/preload preferences between reads; Media3 1.11 CacheWriter bytecode verifies its exception path closes the source and releases the span lock. Adaptive/live sources remain excluded. Startup/rebuffer thresholds are 250/500 ms, with a 32 MiB allocator target and 10-30 seconds of current-video buffering. [judgement] These trade some speculative traffic for quicker swipes while retaining both cache and preload switches.

## Lossless server (opt-in)

**Koda has no lossless server of its own; the listener points it at one** (Settings > Advanced > Lossless audio, `ui/settings/LosslessSettings.kt`). The protocol is the one koda-windows speaks [verified against `LosslessServer.cs`, November 2026; not yet probed against a live server from Android]: `GET {base}/search?q=&quality=&atmos=none` and `GET {base}/stream/{id}?quality=&atmos=none`, the latter answering a DASH manifest or the file itself. With a secret, every call carries `X-LW-TS`, `X-LW-Sign` (HMAC-SHA256 of `"{ts}\n{METHOD}\n{path}\n{token}"`, path without query, token from the `/a/TOKEN` address) and `X-LW-Intent`. Code is `data/lossless/`.

**Settings are their own encrypted store** (`LosslessSettings`, `koda_lossless_server`), read fresh on every decision and deliberately outside `BackupRepository`'s allowlist, because the address carries an access token. It holds no flow; a read before anything was ever saved answers the defaults without opening the keystore. `LosslessQuality` ids are stored and frozen; so is `DOWNLOAD_MUSIC_QUALITY_LOSSLESS`, which rides on `DownloadRequest.audioQuality` into the failed-downloads file. Lossless as the *default* lives in the lossless store, never in `download_music_quality`, so forgetting the server cannot leave downloads asking for one that is gone.

**Matching is strict on purpose.** [judgement November 2026] The Windows client took the first title containing the song's title and failing that `results[0]`, so live takes and other songs were saved silently. `LosslessMatcher` requires the title, the artist where both sides name one, and the length within 12s where both know it, and holds versions the request did not name (live, remix, acoustic, sped up...) against a candidate. Remasters are deliberately not a version. No candidate clearing the bar is "not on your server".

**Streaming is a step in `MusicStreamResolver`, never a replacement for one.** After downloads and the in-memory URI cache, before the disk cache and YouTube, `LosslessStreamSource` asks the server under a 7s budget (well inside the resolver's 20s, so YouTube keeps its full budget). Any failure is null and the old path carries on. A miss rests that song 30 minutes, a failure 10, a 401/403 rests the whole server 5. Streaming defaults to unmetered networks only. A remembered URI only counts while it is the kind wanted now, so flipping the switch applies to the next play.

**A lossless row is marked by its URI fragment** (`LosslessStreamUri`, `#koda-lossless` / `#koda-lossless-dash`). A fragment is never sent and is dropped when a manifest's relative segments resolve against it, and it rides on the URI through `bind`, `replaceMusicSource` and recovery without a field to forget. `LosslessAwareMediaSourceFactory` plays marked rows past the playback cache (DASH for a manifest, since the URL does not say so). [judgement] The music cache is keyed by song id and sized for AAC; FLAC under the song id would later be read back as the YouTube stream. The warmer, AutoMix profiling and the whole-song waveform therefore skip marked rows too: a lossless song mixes as a plain fade and keeps only the live waveform. `PlaybackRecovery` handles a marked row first: one fresh address for a stale one, then YouTube; a decoder, container or audio-track error goes to YouTube at once. A 403 there is the server's and must never re-mint visitorData.

**Downloads join the manifest properly and remux to real FLAC.** `DashManifest` reads `SegmentTemplate` (timeline or fixed duration, `startNumber`, `%0Nd` widths), `SegmentList` and a bare `BaseURL`, where Windows assumed a non-standard `segmentDuration` and fell back to 4s (cutting short or failing on other lengths). Segments are each a bounded request with their own retries. `LosslessAudioFiles` lifts the FLAC frames out of the fragmented MP4 into a `fLaC` stream with the `dfLa` STREAMINFO (no re-encode), so jaudiotagger can tag it (`createMetadataCopy` picks its temp suffix by extension, because the tagger picks its reader that way). ALAC, or FLAC whose header the platform extractor does not expose, stays an `.m4a`; lossy audio is refused. With "Save from YouTube when missing" off, a miss is `LosslessUnavailableException`, which `runTask` does not retry. `DownloadRepository.losslessDownloads` (the `lossless` field in the downloads metadata) is what puts the pill on a Downloads row.

**The pill reads the decoder, not the source.** `PlaybackAudioQuality.from(Tracks)` on the controller's selected audio track, so lossless streams, lossless downloads and device FLAC/ALAC/WAV all show it; it reaches every style through `LocalPlaybackAudioQuality`, provided once in `ExpandablePlayer` beside `LocalPlaybackSpeed`, and each style places `PlayerAudioQualityBadge` under the artist. A FLAC inside MP4 may report no PCM encoding, so its detail can be the rate alone.
