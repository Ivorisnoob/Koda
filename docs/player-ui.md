# Player styles, queues and option sheets (`ui/player/`)

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

**Motion artwork is a hero-art opt-in, not a change to every `SongArtwork`.** `MotionArtwork.kt` owns the expanded player's single muted, audio-disabled decoder and `PlayerArtwork` layers it over the existing static fallback. Only the incoming style and current song receive it; Gesture's neighbouring cards, queues, the mini-player and backgrounds remain static. `MotionArtworkRepository` is player-host scoped (not process-global); its bounded in-memory match cache stores no listening history on disk, and only its expiring public Apple web token and a 32 MB media cache persist under `cacheDir`. `MotionArtworkResolver` matches catalog songs to their actual album relationships and pins one concrete rendition rather than handing an adaptive master to the ABR selector. **How large a rendition is a four-tier picker** (`MotionArtworkQuality`, persisted by `name` and therefore frozen): Saver ~360px, Balanced ~480px at its cheapest encode - the long-standing behaviour and still the default, so no existing install moves - High the largest H.264 rung, Max whatever the ladder carries. [verified September 2026, 346 rungs across 12 square ladders] every rung Apple publishes is `VIDEO-RANGE=SDR`, H.264 stops at 1080x1080 and HEVC continues to 2160x2160, so **there is no HDR tier to offer** and Max is a codec step rather than a dynamic-range one - which is just as well, since the artwork surface is a TextureView and could not present HDR. The resolver returns an ordered **fallback chain** rather than one URL, because Max hands the device a 2160 HEVC clip not every decoder will take and a single playback error used to drop that song to its static cover for good; the chain only ever steps downward, so a failure costs sharpness and never extra data. The lookup cache and the media cache are both keyed or sized by tier - a cache keyed on the track alone would go on serving the old rendition for six hours after the picker moved. The setting defaults off, unmetered Wi-Fi only defaults on, and lifecycle, playback, Battery Saver, Data Saver, animation-scale zero, Local Only and Incognito gate both lookup and playback. Keep this separate from YouTube video playback and audio focus. Apple lookup failures are static artwork, never a playback failure; don't add an opaque proxy or hardcoded bearer as a fallback. [scar] The token scrape shipped on a client built `followRedirects(false)`, and `https://music.apple.com` answers its own root with a **301** to a locale path - so `webToken()` threw on every call, `resolve()` swallowed it, and the entire feature was a silent no-op on every device and every song while looking correct in review. Two things fixed it and both matter: `getWeb` follows redirects itself, checking each hop against `MotionArtworkResolver.isWebUrl` so the client can go on refusing to follow them blindly, and the feature now logs its outcome under the `MotionArtwork` tag. It had **no logging at all**, which is why a dead feature took a live HTTP probe rather than one logcat line to diagnose. Probe the provider before trusting any of this shape - the same rule `youtube-data.md` states for InnerTube applies to Apple.

**The Canvas field is sampled from the cover's edge, and that is the whole trick.** The art fills the top `CANVAS_ART_FRACTION` of the screen and dissolves at its foot into `ui/player/CanvasField.kt`, whose top colour is the average of the artwork's own bottom rows in three columns - so the join is continuous by construction rather than disguised. Two cheaper answers were built first and both failed on the same point: a blurred copy of the cover still carries the cover's edges and composition, so the eye finds where the sharp and blurred versions line up however soft the mask, and a palette-derived cloud supplies a plausible colour rather than *the* colour, which reads as a step at the boundary. [scar] Reaching for `ChromaticMistBackground` also exposed a live defect worth knowing before reusing it anywhere: it early-returns a **flat `fallbackColor`** when `albumArtUrl` is null, and all four of its callers pass `highResThumbnailUrl`, which is null for every device-library song - so on a local file it paints a plain rectangle rather than an ambient background. `CanvasField` reads `thumbnailUrl ?: albumArtUri`, as `SongArtwork` does. Canvas also does not auto-hide its chrome: a full-bleed style is where controls are most wanted and were least often present.

**Naming trap: the `POSTER` enum key is the "Canvas" player.** The old kinetic-type Poster style was rewritten in place as full-bleed album art; the constant and file name (`PosterPlayerContent.kt`) kept the old key for prefs compatibility while every user-facing string says "Canvas". Searching "Canvas" will not find the enum; searching "Poster" lands on a file that does nothing poster-like. **Do not "fix" this** - the stored value is the string `"POSTER"` and renaming resets every user's style.

Adding or renaming a style touches **four** places (an omission compiles but misbehaves): the `PlayerStyle` constant in `ThemePreferences.kt`; a `<Name>PlayerSheetContent(viewModel, ...)` composable in `ui/player/<Name>PlayerContent.kt`; a branch in `ExpandablePlayer.kt`'s `when (playerStyle)`, the only dispatch point; and `playerStyleCatalog` in `PlayerStyleCatalog.kt` (label, subtitle, icon, and the `MaterialShapes` polygon that is the style's die-cut identity in the wheel). **The catalog is the only list** - settings picker, onboarding and `rememberPlayerStyleWheelEntries()` all derive from it. A new style also owes its action row an overflow button in that style's own primitive, last in the row, opening `NowPlayingOptionsSheet`; nothing compile-fails without one, it just quietly has no route to radio, artist, album or share. That used to be three hardcoded lists and the way one went stale. A new style also wants a branch in `PlayerStylePicker`'s `PlayerStylePreview`; that `when` is exhaustive, so a missing one is a compile error rather than a silent gap.

**Swipe-to-skip is one contract in `SwipeToSkip.kt`, not a per-style gesture.** `rememberSwipeToSkip(onNext, onPrevious)` plus `Modifier.swipeToSkip(state)` and `swipeToSkipFollow(state, factor)`; one state is shared by a style's artwork and its title/artist block, so both commit at the same 90dp threshold with the same spring home, and a drag crossing between them cannot skip twice (Compose keeps the gesture with the node that took the down). [scar] It exists because the gesture had been copied by hand into each style and **three of the eight - Classic, Bento, Dial - silently never got one**, while Morph drifted to its own threshold. Two styles keep their own reaction on purpose: **Sticker's peel** throws the art off and slaps the next on (its identity, not a spring-back), and **Gesture's swipe steps the queue** through `onQueueItemChange` because its carousel follows `currentIndex` and would fight a ViewModel skip. **The mini player is deliberately excluded** - horizontal there is dismiss, and one small bar cannot mean both.

**The seek bar is one visual in `ExpressiveScrubber.kt`, and the styles kept their gesture.** Six styles drew `LinearWavyProgressIndicator` with a transparent `Slider` laid over it for touch, so `ExpressiveScrubber` is a drop-in replacement for the *indicator* only: the Slider still owns the drag, the value range, the seek and the accessibility semantics, and publishes the gesture through `LocalPlayerScrubInteraction` for the visual underneath to read. [judgement] Issue #250 asked for a component that replaces the whole stack; taking the gesture off the primary playback control in six styles that each express position differently - two in fractions, four in milliseconds, three calling `viewModel.seekTo` and three an `onSeekTo` lambda - is a much larger risk than the delight is worth, and none of the delight needs it. On touch the thumb blooms from a resting pill into a taller playhead on a bouncy spring, the wave settles flat because a wave travelling under a moving finger reads as the bar lagging behind it, and the waveform bars swell under a soft bell centred on the playhead. **The scrub ticks, and it goes through the app's own haptics.** [scar] This one control called `LocalHapticFeedback` directly, so it went on buzzing for somebody who had set Haptics to off - the exact failure `KodaHaptics` exists to make impossible - and its release effect fired on first composition, giving a confirm buzz every time the player opened or a style crossfaded in, for a bar nobody had touched. Both go through `rememberKodaHaptics` now, and holding the bar ticks once per detent as the playhead crosses it: the detents are the drawn bars taken every third one (10.5dp, about thirty across a phone-width track), because one per bar is a hundred pulses the vibrator smears into a single tone, with a 20ms floor so a flick cannot queue pulses that arrive after the gesture. It reads the *drawn* position rather than the raw gesture, so the tick and the bar passing under the playhead are one event, the rule the video player's level slats already follow; each style feeds a spring-smoothed fraction, so the offset from the finger is constant while a drag moves and what the hand feels is the cadence. The subscription is scoped to the gesture in its own composable, since `progress` changes every frame of playback and a collector left running would wake on all of them. Still missing from #250: chapter and SponsorBlock detents (music mode has neither) and the die-cut `MaterialShapes` bloom, which lost to a pill because the styles give this row only 12-14dp. **Dial and Bento are deliberately not converted** - Dial's progress is a circular dial and Bento's is a tile - and Poster's Slider is visible rather than transparent, so it would need its own treatment.

**A waveform is the whole song, decoded once at load, and then it holds still.** [scar] It was measured only from Koda's own playing PCM, which meant the bar could describe nothing past the playhead: a first listen watched the shape grow and re-scale behind the cursor for three minutes, and the one thing a waveform is for - seeing that the chorus is loud *before* reaching it - was the one thing it could not do. `WaveformAnalyzer` decodes the track in one `MediaExtractor`/`MediaCodec` pass and publishes a complete envelope through `WaveformEnvelope.measured`, which interpolates any bucket the decoder skipped so the result is genuinely `isComplete` rather than nearly so. **A stream is read through the ordinary playback source, and that is the whole design**: a `MediaDataSource` over `CacheManager`'s cache-backed Media3 `DataSource`, opened under the song's own cache key, so invariant 3's bounded ranged requests and `uaForPlaybackUri`'s per-client User-Agent both hold without the analyzer knowing about either, and the bytes it fetches are the same bytes playback is about to read - a song listened through costs nothing extra and starts from disk. Handing the extractor an https URL instead would be an unbounded GET with the wrong UA for bytes nothing else could use. [verified September 2026 against the Media3 1.11.0 bytecode] Reading the song the player is reading is safe rather than merely unlikely to collide: the factory sets no `FLAG_BLOCK_ON_CACHE`, so `CacheDataSource` takes `startReadWriteNonBlocking` and falls through to upstream without caching when the other reader holds the span - no lock waited on, no span written twice. Nothing may set that flag. [judgement] A stream is measured whenever its bytes can be *kept* - the music cache on, and not Local Only - because that is exactly what makes the fetch shared rather than duplicated; with the cache off the pass would pull a second copy nothing else can use, into a store the user switched off. **There is deliberately no metered check**, and an earlier version of this had one: the measurement is of the song being listened to rather than a guess at the next one, so on any connection it is the same bytes moved earlier, and only skipping away mid-song spends more. A connection-shaped rule hid the feature outright from anyone mostly on mobile data, to enforce a preference those two switches already state. A refusal is not a failure - the song keeps the plain wavy bar and gains its shape from being listened to, because `WaveformTap`'s live sampling stays as the fallback for exactly this and for containers no decoder here can open. **`WaveformStore.record` is a no-op once an envelope is complete**, since the two paths measure different signals - the file's own PCM against what the sink was handed after gain and normalisation - and letting a listening sample raise a bucket of an analysed envelope pulls one song's shape out of shape across replays. **The drawn envelope is a frozen snapshot, pinned per song.** `rememberPlayerWaveform` returns null until the store holds enough of the song to draw all of it (90%, because `bars()` interpolates gaps and holding out for the last few buckets leaves a plain bar on a song whose shape is plainly known), then pins a copy that nothing can change under it; `PlayerWaveform` memoizes its resampled bars off that copy, where the old code re-reduced and re-sorted 512 buckets on every frame of playback. [scar] The store's revision was collected *in composition*, so every recorded sample - ten a second, for the whole of every song - recomposed the player host and all eight styles' progress rows; it is collected in an effect now and read exactly once. The in-memory answer is taken during composition so a song whose shape is already stored has it on the first frame, which is what stops `scrubberTrackHeight` collapsing and re-expanding on every track change. **The entrance is `util/WaveformReveal.kt` and it is pure so the JVM suite can hold it to its endpoints**: a constant-rate sweep across the track with an ease-out-back per bar, each rising from a dot on the centre line and springing past its level. Constant rate rather than a spring because a spring drives the *front* of a stagger and every bar past the front is then clamped, so the bounce lands nowhere; the bounce belongs to each bar. `factorAt` returns exactly 1 for every bar once the sweep is done - a curve that settles at 0.98 would leave the waveform permanently 2% short and quietly wrong about the song, which is not something anybody could catch by looking. The measurement rules themselves are unchanged and were their own scar: **the tap carried a *peak* first and the bar drew as a rectangle on nearly every song**, because peak amplitude in anything mastered sits near full scale almost everywhere. Loudness that visibly differs between a verse and a chorus is RMS. Three smoothers came out with it - buckets averaged within a drawn bar, normalisation against the loudest bucket alone (which only guarantees that *one* bar reaches the top), and a sampler so slow each bucket held a single reading. `bars()` reduces by quadratic mean and contrast-stretches between two percentiles of the song's own distribution; a plain maximum was tried in between and is worse than either, because at roughly four buckets to a bar it picks the local loudest every time and every bar converges. A genuinely level song is drawn as a solid band rather than having dynamics invented from noise. The analyzer measures in 100ms windows to match the sampler's cadence, since the two fill the same buckets for songs that get some of each and a shorter window reports a higher RMS for identical audio. A bucket keeps its loudest visit so a replay cannot erode its own peaks, byte 0 means unmeasured and is distinct from a measured silence. `WaveformStore` is process-wide transport like `VisualizerBus` rather than an eleventh entry on invariant 6's list, and its own preference file is **intentionally absent from `BackupRepository`** - a few hundred envelopes riding along in every backup is exactly the weight a derived cache should not add.

**Both pickers show every style.** Onboarding used to offer a curated pair; that was changed deliberately, because people pick a look at first run and were not finding the rest. `PlayerStylePicker` is non-lazy for exactly this reason: it renders inside onboarding's `verticalScroll` column and inside the settings page's `LazyColumn` item, and a lazy grid nested in a scrollable parent has unbounded height.

**Eight styles, three queue views**, and that is the ratio to keep. `ExpressiveQueueView` (Classic), `GestureQueueView` (Gesture) and `EditorialQueueView` (the other six) draw genuinely different rows, so the *behaviour* is shared and the visuals are not. `ui/components/QueueReorder.kt` holds the drag state machine and `QueueRowContainer.kt` the lift, swipe-to-remove, undo snackbar and `QueueDragHandle`. **Both live in `ui/components/` rather than `ui/player/` because video mode's `VideoQueueSheet` uses them too**, which is why `queueRowKeys` takes ids rather than `Song`s. A fourth queue view uses them rather than growing a fourth implementation - that is exactly how reordering ended up in one view of three and removal in two.

**Opening any music queue focuses the current song once.** `rememberFocusedQueueListState` waits until the lazy list is laid out, smoothly brings the current row into view and centers it where the list bounds permit; the two queue designs with a now-playing header pass one leading item. It deliberately does not follow later track changes or restart after an interrupted animation, because once the listener scrolls or reorders, the list belongs to them. Closing and reopening the queue creates a fresh state and focuses again.

Four rules those files enforce, each something that was wrong before:

- **The visible drag handle is the primary path; long press is only the accelerator.** A queue row is tappable, so `Surface(onClick)`'s clickable sits deeper in the modifier chain than a long-press detector on the same row and wins the gesture; and moving before the timeout hands the pointer to the list's scroll. `LibraryScreen`'s playlist reorder splits the same two ways and only gets away with a row long-press because its clickable is *disabled* in manage mode - a queue cannot do that, since tapping a row must skip to that track.
- **The swap is resolved once per frame from a `withFrameNanos` loop, never in the pointer callback.** `layoutInfo` refreshes only after relayout and several pointer events arrive per frame, so a per-event swap measures against a stale snapshot and the row walks away from the finger.
- **Queue row keys are occurrence-qualified, never index-qualified.** A queue can hold the same track twice so a bare id crashes on duplicate keys, but `"$id_$index"` re-keys every row a moved row passed and `animateItem` then has nothing to animate.
- **Auto-scroll only when the list can consume it.** A `scrollBy` the list cannot take is passed on through nested scroll, and the video queue lives in a `ModalBottomSheet` - unguarded, dragging a row against the top drags the sheet closed mid-reorder.

Music writes the session once on release (`moveQueueItem(..., persist = false)` per crossing, then `commitQueueOrder()`); per-crossing writes turned the gesture into stutter.

**Video mode's queue is edited through `VideoQueue` itself, not the ViewModel.** `moved`, `removedAt`, `withInserted` live on the data class because `index` points at the playing video and every edit must keep it there - a reorder crossing the current index shifts it, a removal above it decrements it - and there is no id to fall back on. Two removals are refused outright, with no control offered rather than one that fails: the last remaining entry, and **the entry that is playing**, because video mode has no playback service to hand off to and the player would go on playing a video the queue no longer contains. `enqueueVideo` starts an ad-hoc queue (`VideoQueue.adHoc`, `playlistId` null) from whatever is already playing, which is what makes "add to queue" work from a feed or search. `moveQueueItem` and `removeQueueItem` check `timelineAgreesAt` before touching the player, as `skipToQueueItem` always has: the UI queue and the ExoPlayer timeline can drift, and editing the wrong index is worse than editing none.

**Every style has an overflow button, and it opens the one menu.** `NowPlayingOptionsSheet` (`ui/player/NowPlayingOptionsSheet.kt`) is the playback-speed slider, start-a-radio, add to playlist, like, download, go to artist, go to album and share for the playing song. The speed slider is the one *control* in a sheet of actions and leads it for that reason: everything else is a row you tap once and are done with, while the slider is what someone opens the menu to adjust, and four action rows above it would put it under the fold on a small screen. It applies as it moves and persists on release (`setPlaybackSpeed(..., persist = false)` during the drag), because speed is judged by ear but is one decision rather than forty preference writes. Each style draws the button with its own primitive - `EditorialCircleButton`, `MorphUtilityButton`, `BentoTile`, Classic's `FilledIconButton`, Gesture's plain `IconButton` - because the top bar is part of that style's identity, and **it is last in its action row**, which is where an overflow goes. What it replaced was an Add-to-playlist button, and the eight separate `AddToPlaylistSheet` hosts behind it: one action had a permanent slot in every player while radio, artist, album and share had none, seven of the eight never called `loadYouTubePlaylistsForSheet` so their picker silently listed local playlists only, and six passed `localPlaylists` rather than `addToPlaylistItems`. A ninth style adds a button, not a menu. Go to album is device-library only, and deliberately: `Song.album` is a display string, so it resolves to a real album page for a file on this device (`LibraryContent.initialAlbum`, the same hand-off shape as `initialArtist`) and to nothing at all for a YouTube song. Share is the mirror image - a device file has no link to send. Both are hidden rather than disabled.

**The two option sheets share their rows, not their contents.** `ui/player/PlayerOptionRows.kt` holds `OptionGroup`, `OptionRow`, `OptionRowDivider` and the song header used by both `SongOptionsSheet` (long press) and `NowPlayingOptionsSheet` (the player's overflow), for the reason `QueueReorder.kt` is one file: two menus reached by different gestures must not drift into two different-looking menus. **Both bodies scroll**, and that is load-bearing rather than tidy - a bottom sheet whose content is a plain `Column` clips everything past the sheet's height with nothing logged, identically at every data size, which is how `VideoOptionsSheet` shipped with three unreachable rows. Rows are grouped into shared containers rather than stacked as standalone cards, because six 76dp cards is what overflows in the first place.

**`addToQueue` had no caller for a long time** except the auto-queue, so adding one track to what was playing was impossible. `ui/player/SongOptionsSheet.kt` is the entry point now - Play next, Add to queue, Add to playlist, Like, Download, Go to artist - opened by a long press through `Modifier.songRowClick` and hosted **once** in `HomeScreen` (`songOptionsTarget`), because it acts on the `PlayerViewModel` that lives at that level. Screens take `onSongLongPress: ((Song) -> Unit)?` and pass it down rather than hosting their own. [scar] `onArtistClick` is nullable and that single host was the only call site, so for as long as the row existed it was never once rendered - a nullable wiring parameter defaulting to null is the per-call-site wiring trap in `screens.md`, and one host does not make it safe.
